# 공개 사례는 개발과 오염 진단에 쓰고 새 취약점 발견은 전향적 사례로 판정한다

2026-10-01 결정. 공개 CVE, 보안 권고, 수정 커밋과 PoC는 SystemOne 모델의 학습 데이터에 포함됐을 가능성이 있다. 연구자가 사례를 보지 않도록 봉인해도 모델이 보지 않았다는 뜻은 아니다. 확인한 TypeSafe 공개 자료는 Jev의 학습 방식과 공개 벤치 성적을 설명하지만 정확한 학습 말뭉치와 지식 기준일은 밝히지 않는다. TypeSafe도 공개 벤치가 반복 최적화의 영향을 받는다고 설명하며 비공개 평가를 권한다([Jev 소개](https://typesafe.ai/blog/introducing-system-one-models-and-jev), [공개 벤치에 관한 TypeSafe의 설명](https://typesafe.ai/blog/antibenchmaxxing)).

따라서 평가 사례를 다음 세 역할로 나눈다.

1. **공개 개발군:** 공개 CVE와 공개 벤치로 코드 조회, 실행 하네스, 오라클, PoC 재현과 측정 절차를 개발한다. 이 결과는 알려진 취약 코드 식별에 얼마나 유용한지 보여준다.
2. **오염 진단군:** 공개 사례에서 CVE·프로젝트·버전 등 메타데이터를 제거하고, 수정 버전 대조군, 취약 구문을 제거한 위약 사례, 식별자 변경과 동등한 제어 흐름 같은 의미 보존 변환을 비교한다. 성능 급락이나 근거 없는 정답 반복은 기억 의존 신호로 해석한다. 진단을 통과해도 학습 데이터 비포함을 입증한 것으로 보지 않는다.
3. **전향적 판정군:** 평가 방법과 모델을 먼저 고정하고, 모델 실행 시점에 외부에 공개되지 않은 실제 취약점을 분석한다. 독립 검증과 [PoC 재현 완료 조건](0020-first-study-reproduced-findings.md)을 통과한 결과만 새 취약점 발견으로 센다. 정확한 모델 식별자, 실행일, 프롬프트와 도구 구성, 원본 응답과 캐시, 최초 공개 시점을 보존해 실행이 공개보다 앞섰음을 확인한다.

서비스형 모델의 가중치나 학습 상태가 실행 사이에 바뀌며 정확한 버전을 고정할 수 없다면 그 사실과 기간을 한계로 기록한다. 실행 뒤 처음 공개된 사례를 계속 모으는 방식은 공개 시점이 증명될 때 전향적 판정군에 포함할 수 있다. 사람이 주입한 결함은 통제된 기전 비교에는 유용하지만 실제 새 취약점 발견과 같은 결과로 합치지 않고 보조 실험으로 따로 보고한다.

전향적 판정군의 구체적인 확보 방식, 대상과 규모는 지금 정하지 않는다. 공개 개발군으로 하네스, 비교 조건, 비용 측정과 독립 검증 절차를 안정화한 뒤 후속 단계에서 정한다. 그전에는 전향적 사례를 최적화나 방법 선택에 사용하지 않는다.

이 결정에 따라 공개 사례만으로는 **새 취약점을 발견하는 데 효과적이다**라고 주장하지 않는다. 공개 사례에서는 **알려진 취약 코드 식별과 조사 우선순위에 유용하다**는 범위까지만 주장한다. 새 취약점 발견에 관한 주장은 전향적 판정군의 결과와 그때 실험한 언어, 대상, 취약점 유형, 예산 범위에 한정한다.

[ADR 0013](0013-evaluation-cases.md)의 ARVO 봉인 사례와 Magma 사례는 공개 개발군 또는 오염 진단군으로 유지한다. 기존 결과는 폐기하지 않고 그 주장 범위를 이 결정에 맞춰 해석한다.
