# Jev 협업으로 연구를 다시 설계하고 논문으로 도구의 효과를 검증한다

2026-10-16 기준 합의. Sift의 목표는 **Jev(SystemOne)를 강한 코딩 에이전트와 함께 써서 실제 취약점 발견의 시간·비용 대비 성과를 높일 수 있는지** 확인하고, 그 방법을 구현한 도구와 효과를 검증하는 논문을 내는 것이다. 논문은 도구 자체를 대신하는 산출물이 아니라 도구의 방법과 효과를 검증하는 수단이다. 이전의 함수 전수 선별 → 관계 후보 재선별 → 심층 분석이라는 고정 3단계, Jev 2차 필수, 대상별 분석기 구축 가이드, 코드 비율 recall 목표, 싱크 슬라이스 개발, 이전 첫 비교의 Pi/Muse 모델 고정을 활성 연구 계약에서 내린다. 기존 문서·실험·구현과 로컬 원자료는 별도의 보존 폴더로 분리한다. 신규 방법이 이전 연구의 한 선택에 자동으로 묶이지 않게 하면서, 이미 지출한 실험과 그 한계는 훼손하지 않기 위한 결정이다.

## 연구와 평가의 합의 범위

- 첫 범위는 C/C++ 오픈소스의 메모리 안전성에 대한 **white-box** 조사다. 에이전트에는 고정된 소스·빌드·테스트 환경을 주되 취약점 설명과 위치는 주지 않는다. 실행에 필요한 의존성을 미리 준비하고 일반 인터넷은 차단하며 모델 통신만 허용한다. 모든 비교군에 같은 네트워크·대상 정책을 적용한다.
- 주 모델은 **Jev**다. 강한 에이전트 단독, 같은 총예산을 나눠 쓰는 동종 강한 에이전트 복수 실행, 강한 에이전트와 Jev가 협업하는 방식의 세 조건을 비교한다. 조건별 금전 비용 상한과 최대 실행 시간을 같게 하고, 먼저 닿는 상한에서 중단한다. 구축·모델·도구·재현 비용과 시간도 기록한다. Jev가 맡을 판단과 적응적 협업 정책은 아직 정하지 않았다.
- 첫 개발 실험의 강한 에이전트는 **Claude Code + 사용자가 지칭한 Mythos 5.1**로 잠정 선택했다. 정확한 모델 식별자·접근 조건은 실행 전에 확인해 기록한다. 통제 평가에서 강한 코딩 에이전트 두 계열로 모델 종속성을 살피고, 전향적 평가에서는 개발 결과를 보고 한 계열을 미리 고정한다. 강한 에이전트를 하나로 고르는 기준, 실행 설정과 반복 횟수는 개발 파일럿에서 정하고 본 평가 전에 고정한다.
- 성공은 위치·발생 조건·근본 원인·보안 영향을 설명하는 보고서와 **취약판에서 재현되고 수정판에서 같은 PoC가 기대한 이유로 실패하는 결과**가 독립 검증을 통과한 경우다. 후보·순위·코드 비율 recall은 중간/진단 지표다. 신규 결함의 수정판이 아직 없으면 확인 전 상태로 남긴다. CVE·패치·권고는 가치 있는 외부 성과이지만 발급이나 공개 일정이 외부에 달려 있으므로 주 성공 기준은 아니다.
- 평가는 두 층이다. 공개된 과거 사례는 개발과 오염 위험을 명시한 통제 평가에 사용한다. 신규 발견 주장은 방법·모델·평가기·예산을 먼저 고정한 **전향적** 실제 프로젝트에서만 한다. 대형 앵커 프로젝트 1개와 공격 표면이 다른 2~4개 프로젝트를 사전 선정 기준과 고정 커밋으로 정한다. 각 프로젝트 안에서 세 조건을 격리된 독립 실행으로 비교하고, 프로젝트 사이에서는 원시 결함 수를 직접 합산해 일반화하지 않는다. 반복 횟수는 개발 파일럿의 비용·변동성을 본 뒤 본 평가 전에 고정한다.
- 전향적 실행은 로컬 복사본·격리된 서비스에서만 진행한다. 에이전트가 실제 운영 서비스 공격, 외부 신고 또는 공개를 직접 하지 않는다. 연구자가 공식 비공개 채널로 유지관리자에게 알리고 패치·공개 일정을 조율한다. 공개 전 세부 PoC를 저장소·논문에 내지 않으며 embargo 중이면 익명화한다.

## 아직 정하지 않은 것

Jev의 구체적 역할과 질문, agent harness의 차별적 적응 방법, 작업·상태 표현, 도구의 CLI/배포 형태와 모델 어댑터, 예산 계산 방식, 통제 평가 표본·에이전트 설정, 전향적 대상의 이름·커밋과 검증 오라클은 후속 설계·파일럿의 대상이다. 자율성을 막는 고정 파이프라인도, 모델이 모든 결정을 맡는 자유 실행도 미리 채택하지 않는다. 추가 전용 이벤트 기록·조사 그래프와 coordinator/harness 분리는 논의한 아이디어지만 구체적 제품 계약으로 확정하지 않는다. 도구 형태를 정할 때 기존 제품 조사를 출처와 함께 다시 검토한다.
