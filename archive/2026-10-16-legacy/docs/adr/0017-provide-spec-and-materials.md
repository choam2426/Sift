# Sift는 완성된 도구가 아니라 에이전트가 대상에 맞게 구축할 분석기의 설계·스펙·재료다

> 재검토 상태: 2026-09-29 언어 중립 적합성 시험 모음은 만들지 않는다. 스펙에는 점검 항목만 두고, 에이전트가 검사를 직접 만든다. 같은 날 종단 실험에서 두 에이전트가 스펙만 보고 만든 검사(47개, 27개)로 참조 구현과 같은 추출을 얻었고, 비용 대비 효과가 작다고 봤다. 아래의 "적합성 시험"은 이 점검으로 읽는다.

2026-09-29 결정. Sift는 완성된 분석기를 배포하지 않는다. 연구원이 자신의 에이전트에게 "Sift를 분석 대상 X에 맞게 구축해줘"라고 요청하면, 에이전트가 Sift가 제공하는 설계와 스펙을 따라 대상에 맞는 1차·2차 입출력을 구성하고, 적합성 시험과 벤치로 확인한 뒤 스캔한다. [ADR 0015](0015-agent-harness-direction.md)의 방향(연구원의 에이전트에 붙어 Jev로 우선순위를 정한다)은 유지하고 제공 형태를 정한다.

## 이유

범용 분석기는 가능하지 않다. 버그 유형이 많고, 같은 첫 프로파일 안에서도 좋은 2차 묶음 규칙이 사례마다 달랐다. 설계용 라벨 5개에서 7-Zip·zlib·libexpat은 피호출자 묶음(A)으로 충분했고, libtiff는 형제(D)나 2홉(E)이 필요했으며, stb는 어떤 규칙으로도 필수 줄을 모두 담지 못했다([실험 요약](../../experiments/README.md)). 하나의 규칙을 모든 대상에 맞추려면 사례를 늘리며 쫓아가야 한다. 반면 대상에 맞춰 빌드 방식을 파악하고, 언어에 맞는 추출을 고르고, 도메인에 맞는 질문과 규칙을 고르는 일은 에이전트가 잘한다.

그러나 전부를 에이전트에게 맡기면 틀려도 멀쩡해 보이는 함정을 대상마다 다시 밟는다. 2026-09-27~28에 겪은 예: tree-sitter가 문장 매크로 때문에 `MixCoder_Code`를 2천 줄 뒤에서 끝내고 Zstd 디코더를 통째로 놓쳤다. 구성마다 시작 줄이 달라 같은 함수가 이중 평가될 뻔했다. 잘린 캐시 줄이 재개를 망가뜨렸다. 토큰 추정이 2배 넘게 틀렸다. 그래서 보장해야 할 것은 스펙과 적합성 시험으로 고정하고, 대상별로 바꿀 것만 에이전트가 구성한다.

## 제공물

| 제공물 | 내용 |
|---|---|
| 설계 | 3단계 구조, 각 단계의 역할과 입출력, 고정된 것과 대상별로 바꾸는 것, 근거와 한계 (`DESIGN.md`) |
| 스펙 | 각 부분이 보장해야 할 것, 실행 디렉터리 형식, Jev 호출 규칙. 구현이 만든 실행 디렉터리를 검사하는 언어 중립 **적합성 시험**(입력, 기대 결과, Jev 모의 응답)을 포함한다 |
| 보일러플레이트 | 참조 구현(현재의 `sift` 패키지와 테스트). 에이전트의 출발점이며 스펙의 일부가 아니다 |
| 벤치 | 라벨 사례, 측정 도구(1차 순위, 묶음 도달률, 기준선 대비 순위), 대상 자신의 과거 보안 수정으로 구성을 검증하는 절차 |
| 질문 라이브러리 | Jev 질문의 문구, 버전 해시, 측정 성적, 기각된 질문과 이유 |
| 운영 스킬 | 연구원과 함께 분석하는 절차, 판정 기록, 범위 보고, 서브에이전트 위임, 보고서 양식 |
| 설치 가이드 | 구축 절차, 대상 유형과 무관한 일반 원칙, 비용 가이드 |
| 결과 환류 양식 | 대상, 구성, 벤치 결과, 구축 중 겪은 문제를 기록해 저장소로 돌려보내는 형식 |
| 실험 | 결정의 근거와 기록 |

적합성 시험은 "구현이 스펙대로 동작하는가"를, 벤치는 "이 구성이 이 대상에서 버그에 닿는가"를 확인한다. 둘 다 통과해야 스캔한다.

대상 유형별 레시피(CMake, autotools, 헤더 전용 등)는 모든 경우를 미리 다룰 수 없어 제공하지 않는다. 유형과 무관한 원칙은 설치 가이드에, 구축 중 겪은 구체적인 문제는 결과 환류로 쌓는다.

## 이전 결정에 미치는 영향

- [ADR 0011](0011-vulnerability-type-profiles.md): 유형 프로파일은 에이전트가 대상에 맞게 고르는 구성이 되고, 질문은 질문 라이브러리에서 고른다.
- [ADR 0012](0012-v0.1.0-first-release-scope.md): v0.1.0의 산출물과 배포 기준을 이 제공물 기준으로 다시 정한다.
- [ADR 0016](0016-second-pass-bundle-principles.md): 보편 묶음 규칙을 찾지 않는다. 규칙 후보와, 벤치로 대상별 규칙을 고르는 절차를 제공한다.
- 제품 명세(`docs/product.md`)는 설계 문서와 겹쳐 `DESIGN.md`로 합친다.

## 한계

- 과거 보안 수정에 맞춘 구성이 새 버그를 놓칠 수 있다. 과거 수정이 적은 대상에서는 벤치 검증이 약하다.
- 대상마다 구성이 달라 결과를 서로 비교하기 어렵다. 실행 기록에 구성을 모두 남긴다.
- 구축과 검증에 에이전트 비용과 Jev 비용이 든다. 한 번 구성하면 같은 대상의 다음 버전에 다시 쓴다.
- Jev 우선순위가 에이전트를 더 효율적으로 만든다는 핵심 가정은 여전히 검증 전이다([ADR 0015](0015-agent-harness-direction.md)).
