# 1차는 함수 본문만으로 조사 가치를 평가한다

> 2026-09-28 변경: 선별 기준은 아래 마지막 절의 "`Noul ≥ 0.60`이면서 프로젝트별 상위 15%"다. 그 앞의 `0.60` 단독 기준은 당시 결정의 기록이다.

> 재검토 상태: 2026-09-29 [ADR 0017](0017-provide-spec-and-materials.md)에 따라 질문, 하한, 상위 비율은 에이전트와 사용자가 대상에 맞게 고르는 파라미터다([스펙](../../spec/README.md) P-TRIAGE-QUESTION, P-SELECT). 아래 값은 Sift의 실험에서 쓴 값과 그 근거다.

Sift의 1차 기본안은 모든 함수의 전체 본문을 Jev에 각각 제공하고 `Is this function worth a security researcher's time to inspect further for bugs?`라는 단일 `Noul` 질문으로 조사 가치 순위를 얻는 것이다. 다른 함수 본문과 관계를 따라가는 일은 2차에 맡긴다. 1차에서 모든 버그 관련 함수를 직접 선발하려는 목표 대신, 빠르게 유망한 출발점을 남기는 목표를 택했다.

[파일 전체 표본 실험](../../experiments/archive/first-pass/contrastive/README.md)의 공개 취약점 6개에서 이 질문은 각 파일 상위 10% 선발 시 세 반복 모두 5개 기전에 도달했다. 더 복잡한 대조 판단 질문은 3개, 함수 길이 기준은 4개였다. [선언 추가 실험](../../experiments/archive/first-pass/declarations/README.md)에서 클래스·모듈 선언을 모든 함수에 붙여도 5개로 같았고 입력 토큰이 약 33% 늘었다. 두 실험은 `jev-1.13.0`에서 실행했다. 따라서 더 복잡한 질문이나 선언 추가를 기본안으로 채택할 근거가 없었다.

첫 구현에서는 성공적으로 평가한 함수 중 `Noul ≥ 0.60`인 것만 2차로 추출한다. 같은 277개 함수에서 이 기준은 반복별 40~42개(약 14~15%)를 통과시키고 알려진 6개 기전 중 5개를 남겼다. `0.65`도 5개였지만 통과한 취약 함수 하나의 점수가 `0.68~0.69`여서 여유가 작았고, `0.70`은 4개로 줄었다. 선별 기준에는 모델·질문·입력 표현의 버전을 기록하고 그 요소가 바뀌면 `0.60`을 그대로 적용하기 전에 확인한다.

이 수치는 여섯 개의 소스 코드 사례에서 얻은 결과이며 제품의 재현율이나 최적 성능을 뜻하지 않는다. 별도 탐색 표본에는 `0.54`를 받은 취약 함수도 있었다. 디컴파일 코드의 점수 분포와 1차 선발 유닛에서 2차 관계를 따라 취약 동작에 도달할 수 있는지는 검증 대상이다. Jev 점수는 버그 확률이나 finding 근거로 표시하지 않는다.

2026-09-24에 [C·C++·Rust·Go·Python의 여섯 프로젝트로 확장한 1차 채점](../../experiments/archive/first-pass/README.md)에서도 **첫 A 기준선의 `0.60`은 유지**하기로 했다. 입력 형식을 함수 코드만으로 통일한 결과, 통과율은 TinyXML2 13.7%부터 7-Zip 62.5%까지 달랐다. `tar`의 `unpack_dir`(0.51)와 `go-jose`의 `decompress`(0.59)는 직접 통과하지 않았지만, 관계를 확인할 만한 호출자 또는 관련 함수는 통과했다. 따라서 이 확장 결과만으로 언어별 임계값을 새로 정하지 않는다. 이는 `0.60`의 최적성이나 알려지지 않은 결함의 도달을 입증한 결정이 아니다. A 실행에서는 프로젝트별 2차 처리량과 관계를 통한 실제 도달을 기록하고, 입력 표현·모델·질문이 바뀌면 기준을 재검토한다.

## 2026-09-28: 절대 임계값에서 "하한 + 프로젝트별 상위 비율"로

**선별 기준을 `Noul ≥ 0.60`이면서 프로젝트 안에서 점수 상위 15%인 함수로 바꾼다.** 순위는 점수 내림차순, 동점은 함수 ID 순이고, 비율은 프로젝트의 전체 함수 수로 계산한다. [ADR 0015](0015-agent-harness-direction.md)의 방향에서 1차 결과는 에이전트가 읽을 출발점 목록이므로, 짧고 프로젝트마다 크기가 고른 목록이 필요하다. `0.60`만 쓰면 통과율이 TinyXML2 13.7%에서 7-Zip 62.5%까지 달라져 7-Zip은 602개 중 376개가 남았다.

근거는 1차 실험의 여섯 프로젝트에서 알려진 결함에 닿는 가장 높은 함수의 순위다.

| 사례 | 결함 지점 함수 | 결함으로 이어지는 호출자·진입점 |
|---|---|---|
| Expat R_2_5_0 | `XML_Parse` 상위 3.2% | 같음 |
| TinyXML2 10.0.0 | `GetCharacterRef` 상위 0.8% | 같음 |
| 7-Zip 26.01 | `MixCoder_Code` 상위 11.3% | `XzUnpacker_Code` 상위 0.5% |
| urllib3 2.5.0 | `HTTPResponse.read_chunked` 상위 3.2% (0.78) | 같음 |
| go-jose v4.0.0 | `inflate` 상위 35.8% | `DecryptMulti` 상위 1.7% |
| tar 0.4.44 | `unpack_dir` 상위 41.1% | `EntryFields::unpack` 상위 0.3% |

상위 15%에서는 여섯 사례 모두 결함에 닿는 함수가 들어가고, 결함 지점 자체는 네 사례에서 들어간다. go-jose와 tar는 호출자에서 따라 내려가야 하므로 탐색 중 재선별이 필요하다. 절대 임계값 `0.80`은 urllib3(0.77~0.78)를 놓쳐 기각했다. 10%는 7-Zip 결함 지점(11.3%)이 빠지고, 15%와 20%는 이 데이터로 구분되지 않아 더 짧은 쪽을 골랐다. 하한 `0.60`은 알려진 사례를 하나도 자르지 않으며(결함에 닿는 함수는 모두 0.77 이상), 점수가 전반적으로 낮은 프로젝트에서 목록을 억지로 채우지 않게 한다. Expat 실제 실행에서는 305개 중 46개가 선별됐고 최저 점수는 0.74였다.

**재검토 조건:** 15%는 이미 여러 번 본 여섯 사례에서 고른 값이다. [봉인 사례](0013-evaluation-cases.md)에서 결함에 닿는 함수가 상위 15% 밖에 있으면 비율을 다시 정한다. 모델·질문·입력 표현이 바뀌어도 다시 확인한다.
