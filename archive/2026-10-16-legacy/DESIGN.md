# Sift 설계

2026-10-12 기준. 결정의 기록과 근거는 [`docs/adr/`](docs/adr/)와 [`experiments/`](experiments/README.md)에 있다.

## 1. 연구 목표와 기존 접근

**연구 목표.** Jev 같은 SystemOne 모델을 사용해 취약점을 더 빠르고 효율적으로 찾아낼 수 있는지 연구한다. 2026-10-01에 목표부터 다시 논의하며 확인한 목적이다([ADR 0019](docs/adr/0019-systemone-vulnerability-research-goal.md)).

**최종 제공 목표.** 연구 결과를 바탕으로 사용자가 자신이 분석하려는 대상에 맞는 Sift를 구축할 수 있도록 가이드를 제공한다. 연구에서 확인한 효과와 적용 조건, 한계가 구축 방법의 근거가 된다. 가이드의 구체적인 구성과 검증 절차는 연구 결과에 맞춰 정한다.

SystemOne 모델의 활용은 연구 주제다. 모델이 맡을 판단, 분석 단위와 단계 구성은 이 목적에 맞춰 재검토한다. 평가는 동등한 발견 성과에서의 총비용·시간, 동일 예산에서의 발견 성과, SystemOne을 사용하지 않는 비교군과의 차이, 다른 대상·취약점 유형에서의 적용 조건을 살핀다. 구체적인 비교군, 측정 방법과 수치 기준은 후속 논의에서 정한다.

**첫 실험의 발견 완료 조건.** PoC로 확인할 수 있는 취약점을 대상으로, 독립 검증을 통과한 보고와 PoC 재현까지를 발견으로 인정한다. 보고에는 위치, 발생 조건, 결함의 원인과 보안상 영향이 있어야 한다. 의심스러운 위치 선별과 재현 전 후보는 중간 성과로 기록한다. 재현 환경 준비와 입력 생성 비용도 측정하며, 결론의 적용 범위는 실험한 취약점 유형에 한정한다([ADR 0020](docs/adr/0020-first-study-reproduced-findings.md)). 구체적인 대상과 유형은 다음 논의에서 정한다.

**평가군과 주장 범위.** 공개 CVE와 공개 벤치는 모델이 학습했을 가능성을 배제할 수 없으므로, 구현·하네스 개발과 알려진 취약 코드 식별 성능의 측정에 쓴다. 메타데이터 제거, 수정 버전, 취약 구문을 제거한 위약 사례, 의미 보존 변환으로 기억 의존 신호를 진단하지만, 이 결과만으로 학습 오염이 없다고 판정하지 않는다. 새 취약점 발견 효과는 모델과 방법을 먼저 고정한 뒤 실행 시점에 공개되지 않은 전향적 사례에서 판정한다. 정확한 모델 버전, 실행일, 캐시와 공개 시점을 보존한다. 사람이 주입한 결함은 보조 결과로 분리한다. 전향적 판정군의 구체적인 확보 방식과 구성은 공개 개발군으로 절차를 안정화한 뒤 정한다([ADR 0021](docs/adr/0021-prospective-cases-for-novel-discovery.md)).

**첫 비교 실험의 Jev 역할.** Sift 주 비교군은 아래 3단계 구조의 1차 함수 전수 선별과 2차 관련 코드 후보 재선별에 Jev를 사용한다. Sift군에는 사전 계산한 순위를 주지 않는다. 에이전트가 Sift 구축 방법과 공통 재료, Jev 사용 수단을 받아 대상별 두 단계를 구축하고 실행한다. 구축과 두 Jev 단계의 비용도 종단 측정에 포함한다. 1차만 실행하는 구성은 단계 기여를 분리하는 절제 비교군이며 Sift 주 비교군으로 부르지 않는다. 이 결정은 CyberGym 파일럿에서 상위 파서를 골랐지만 저순위 피호출자의 실제 결함을 놓친 결과에 따라 [ADR 0022](docs/adr/0022-first-comparison-uses-one-jev-stage.md)를 [ADR 0025](docs/adr/0025-restore-second-jev-stage.md)로 대체한 것이다. 첫 C/C++ 2차는 호출지점 경계 비교([ADR 0026](docs/adr/0026-prioritize-callsite-candidates-and-adaptive-expansion.md))를 구조 준비까지 한 뒤 싱크 역방향 슬라이스와 자체 데이터플로우 라이브러리로 방향을 바꿨지만([ADR 0027](docs/adr/0027-sink-slices-with-own-dataflow-library.md)), libpng 파일럿의 낮은 낙관적 상한과 큰 실행 비용을 근거로 2026-10-12 중단했다([ADR 0028](docs/adr/0028-stop-sink-slice-second-pass.md)). 후속 C/C++ 2차 구조는 정하지 않았다.

**첫 비교 실험의 에이전트 환경.** 두 군 모두 최소 Pi 에이전트 `0.99.2`, Pi 내장 `meta` 공급자의 OAuth 로그인, `muse-spark-1.3-contributor`, reasoning effort `high`를 사용한다. 별도의 Meta 인증 확장은 쓰지 않는다. 이 조합은 공개 개발·평가군에만 적용하며, 원격 모델 변경을 추적하기 위해 실행일과 실제 모델 식별자·사용량을 기록한다([ADR 0024](docs/adr/0024-fix-pi-muse-contributor-high.md)).

**공개 벤치의 기준점.** C/C++ 메모리 안전성 실험은 취약점 설명을 주지 않는 CyberGym Level 0을 기준 벤치로 사용한다. 공식 10개 부분집합은 설치와 Sift 연결을 확인하는 파일럿에만 쓰고, 효과 비교용 표본은 후속 선정 절차로 고정한다. 에이전트에는 취약판만 주고, 평가기가 숨긴 수정판에서 최종 PoC 하나를 교차 검증한다. 여기에 독립적인 원인·영향 보고서 검증을 추가한다. Rust·Go·Python·JavaScript와 비충돌형 취약점은 같은 과제 계약과 유형별 실행 오라클로 확장한다([ADR 0023](docs/adr/0023-use-cybergym-level-0-as-c-anchor.md)).

**기존 접근의 적용 상태.** 아래 접근과 2~5절은 2026-10-01까지 구현·시험한 설계다. 기존 스펙과 실험을 해석하는 근거로 보존하며, 앞으로의 연구 구조는 별도로 합의한다.

취약점 연구원은 에이전트(Claude Code, Codex 등)와 함께 코드를 읽고 가설을 세우고 검증한다. 에이전트는 큰 코드베이스에서 어디를 먼저 읽을지 정하는 데 비싼 주의를 쓴다. Sift는 **에이전트가 Jev로 효율적으로 우선순위를 정하게 하고, 무엇을 평가하고 조사하고 기각했는지 기록하게 하는** 분석기의 설계다.

Sift는 완성된 도구가 아니다. 연구원이 에이전트에게 "Sift를 분석 대상 X에 맞게 구축해줘"라고 요청하면, 에이전트가 이 설계와 [스펙](spec/)을 따라 대상에 맞게 구현·구성하고, 스펙의 점검 항목과 [벤치](bench/)로 확인한 뒤 스캔한다([ADR 0017](docs/adr/0017-provide-spec-and-materials.md)). 버그 유형과 대상이 다양해 하나의 구성이 모든 대상에 맞을 수 없기 때문이다.

Jev 점수는 순서를 정하는 신호이며 버그 확률로 표시하지 않는다. 심층 분석, 검증, PoC와 판정 기준은 연구원과 에이전트의 일이다. Sift는 판정을 요구하지 않고 기록한다.

**기존 선별 실험의 후보 축소 목표.** 1차·2차가 3차에 넘기는 후보를 코드 양으로 센다. 아래 수치는 기존 선별 접근의 목표이며, 연구 전체의 성공 기준은 새 연구 목적에 맞춰 다시 정한다([ADR 0018](docs/adr/0018-candidate-goal-by-code-share.md), [0019](docs/adr/0019-systemone-vulnerability-research-goal.md)).
- 합격선: 코드 30% 이내에 벤치 버그 70% 이상
- 도전 목표: 코드 10% 이내에 70% 이상, 그리고 30% 이내에 90% 이상

유닛 개수로 세지 않는 이유는, 긴 함수를 고르는 순서가 적은 개수로 많은 코드를 넘기기 때문이다. 이 실험에서는 코드 양을 3차 읽기 비용의 근사로 사용했다. 실제 취약점 발견까지의 시간·비용 절감은 확인하지 않았다. 2026-10-01 현재 이 후보 축소 목표에 닿은 방법은 없다(6절).

분석 대상은 소스 코드베이스, 바이너리(에이전트가 Ghidra 등으로 디컴파일), 연구원이 이미 디컴파일한 결과다. 대상의 모든 분석 유닛을 평가하고, 평가하지 못한 부분을 명시한다([ADR 0002](docs/adr/0002-complete-unit-evaluation.md)).

## 2. 3단계 구조

| 단계 | 누가 | 입력 | 출력 | 역할 |
|---|---|---|---|---|
| 1차 전수 선별 | 구축된 분석기 + Jev | 대상의 모든 함수 | 출발점 목록 | 전체를 빠짐없이 싸게 훑는다 |
| 2차 관련 코드 재선별 | 구축된 분석기 + Jev | 출발점에서 만든 관계 후보 | 에이전트가 볼 순서와 시작 패킷 | 함수 하나로는 안 보이는 관계를 본다 |
| 3차 심층 분석·검증 | 연구원의 에이전트 + [운영 스킬](skill/) | 순서와 시작 패킷 | 판정 기록 | 관계를 따라가고, 확인하고, 연구원과 판단한다 |

**1차.** 함수마다 원문을 Jev에 보내 조사 가치를 묻고, 점수에 선별 규칙을 적용해 출발점을 고른다. 질문과 선별 규칙은 대상에 맞게 고른다. Sift의 실험에서는 조사 가치 질문 하나와 "점수 0.60 이상이면서 대상 안 상위 15%"를 썼다. 절대 기준만 쓰면 선별량이 대상마다 13.7%~62.5%로 흔들렸다([ADR 0004](docs/adr/0004-first-pass-function-triage.md)).

**2차.** 출발점에서 함수 하나로는 보이지 않는 관계 후보를 만들고 Jev로 다시 평가한다([ADR 0010](docs/adr/0010-three-stage-structure.md)). 규칙은 대상의 버그 모양에 맞춰 벤치를 거쳐 고른다. 큰 함수 묶음 전체에 점수 하나를 주는 기존 A·B·D·E 실험은 크기 편향과 낮은 판별력 때문에 제외했다. 호출지점 경계 비교는 [ADR 0026](docs/adr/0026-prioritize-callsite-candidates-and-adaptive-expansion.md)에 구조 준비 결과로 남는다. 첫 C/C++ 후보였던 싱크 역방향 슬라이스도 낮은 낙관적 상한과 큰 실행 비용 때문에 중단했으며([ADR 0027](docs/adr/0027-sink-slices-with-own-dataflow-library.md), [0028](docs/adr/0028-stop-sink-slice-second-pass.md)), 후속 구조는 정하지 않았다. 2차는 1차 순위만 쓰는 것보다 종단 성과가 나을 때만 채택한다.

**3차.** 에이전트가 순서대로 시작 패킷을 받아 조사하고, 후보에 넣지 못한 관계를 따라가며, 판정을 기록한다. 비싼 판단은 에이전트가, 결과로 검증할 수 있는 기계적 작업은 싼 서브에이전트가 맡는다.

## 3. 범위 기록

세 단계에 걸쳐 다음을 실행 디렉터리에 남긴다. 판정 파일은 사람과 에이전트가 함께 쓰도록 추가 전용이다.

| 분류 | 조건 | 출처 |
|---|---|---|
| 확인된 버그 | 에이전트가 재현을 기록했다 | 판정 기록 |
| 근거 있는 후보 | 에이전트가 근거와 함께 후보로 기록했다 | 판정 기록 |
| 기각 | 에이전트가 이유와 함께 기각했다 | 판정 기록 |
| 배부됐으나 판정 없음 | 순서로 넘겼지만 기록이 없다 | 분석기 |
| 미평가·못 봄 | 한도 초과, 오류, 예산 부족, 어떤 구성에서도 컴파일되지 않은 코드 | 분석기 |

평가하지 못한 것은 알 수 있는 만큼 보고하고, 구현이 보고할 수 없는 것은 무엇인지 적는다. 조용한 누락을 피하는 것이 목표다. 참조 구현은 줄 단위까지 보고한다.

## 4. 고정된 것과 대상별로 바꾸는 것

| 고정 (스펙이 보장) | 대상별로 바꿈 (에이전트가 구성) |
|---|---|
| 3단계 구조와 각 단계의 역할 | 함수 추출 방법 (언어, 빌드 방식, compile DB) |
| 모든 유닛 평가, 못 본 것은 보고 | 버그 유형과 질문 ([질문 라이브러리](questions/)에서 선택) |
| 같은 후보 상태를 두 번 평가하지 않음, 선별은 점수에 대한 결정적 규칙 | 선별 규칙과 그 값, 관계 후보·확장 규칙과 입력 한도 (벤치로 검증해 선택) |
| Jev 호출 규칙 (캐시, 재개, 예산, 계정 오류에서 멈춤) | 대상 범위, `#if` 구성 탐색 범위, 요청 제한 |
| 고른 값과 이유, 판정, 범위 보고를 기록 | |

고르는 값은 [스펙](spec/)에 파라미터로 정의돼 있고, Sift의 실험에서 쓴 값은 예시와 근거로만 적혀 있다.

C/C++ 추출의 기본은 libclang이다. 실제 전처리로 매크로를 처리하고, compile DB 구성·다른 타깃·조건 매크로 켜고 끄기로 도달할 수 있는 모든 구성을 본다([ADR 0014](docs/adr/0014-python-asyncio-and-code-lookup.md)). 전처리기가 없는 언어는 tree-sitter나 언어의 공식 파서로 충분하다.

## 5. 구성을 확인하는 방법

1. **스펙 점검:** 구현이 스펙대로 동작하는가. 에이전트가 스펙의 점검 항목으로 검사를 직접 만들어 확인한다. Sift는 시험 모음을 제공하지 않는다. 2026-09-29 종단 실험에서 두 에이전트가 스펙을 보고 만든 검사로 참조 구현과 같은 추출을 얻었다.
2. **벤치:** 이 구성이 이 대상에서 버그에 닿는가. 대상 자신의 과거 보안 수정을 라벨로 삼아, 수정 전 리비전에서 결함 함수의 1차 순위와 2차 묶음의 도달을 잰다. 최종 후보 순서가 코드 양 일정 비율 안에 담는 버그의 비율을 1절의 목표와 비교하고, 무작위 순서와 긴 함수부터 읽는 순서도 함께 보고한다. 기준에 못 미치면 구성을 고친다.
3. **스캔:** 두 단계를 통과한 구성으로 대상 전체를 스캔한다. 구성과 검증 결과를 실행 기록과 [결과 환류](reports/)에 남긴다.

## 6. 근거와 한계

근거 있는 것 (실험 요약 참조):
- 1차 질문은 Python 6개 사례에서 상위 10% 예산으로 5/6 기전에 도달했다. 새 추출로 한 Expat 실행에서 같은 함수의 점수 차이는 평균 0.011이었다.
- 상위 15%는 1차 실험의 6개 사례 모두에서 결함에 닿는 함수를 포함했다. 이를 정할 때 쓰지 않은 4개 사례에서 결함 지점은 3개가 들어가고 libtiff(24.5%)가 빠졌다. Magma의 버그 38개(libpng·libtiff·libxml2)에서는 유닛 15%에 25개, 25%에 32개, 50%에 37개가 들어갔다.
- 같은 Magma 버그로 호출 그래프 규칙과 질문 추가로 1차 순위를 보강해 봤지만, 같은 유닛 수 예산에서 1차 순위만 쓸 때보다 덜 닿았다.
- libclang 추출은 Expat·TinyXML2·7-Zip의 기준 목록을 모두 찾았고, 기준 구성만 쓸 때보다 7-Zip에서 함수를 약 17% 더 봤다.
- 2차 묶음은 설계용 라벨 5개 중 3개에서 피호출자만으로, 4개에서 형제나 2홉까지 넣어 필수 줄을 모두 담았다.

한계로 드러난 것:
- **1차 점수는 대부분 함수 길이를 따른다.** Magma 3개 대상에서 Q0 점수와 로그 길이의 상관은 0.71~0.80이었다. 유닛 상위 10%가 코드의 30~34%를 차지했다.
- 예산을 코드 양으로 세면 이미 본 3개 대상에서 Q0 순서는 10%에 3개(8%), 30%에 16개(42%)가 들어갔다. 무작위 순서의 평균은 5.2개와 14.4개로 비슷했다([ADR 0018](docs/adr/0018-candidate-goal-by-code-share.md)). 위의 유닛 기준 성적은 이 효과를 포함한 값이다.
- **길이와 버그의 관계는 대상마다 다르다.** 안 본 Magma 3개 대상(libsndfile·lua·poppler, 버그 44개)에서 Q0 원점수는 코드 30%에 23개(52%)로 무작위(13.4개, 30%)보다 나았다. 이 대상들은 버그 함수가 훨씬 길었다(중앙값 135줄·80줄). 길이 추세를 빼는 보정은 이미 본 대상에서 26개로 올랐지만, 안 본 대상에서는 19개로 떨어졌다(2026-10-01, 사전 등록 판정).
- 2026-10-01 기준 ADR 0018 합격선(코드 30%에 70%)에 닿은 순서는 없다. 가장 좋은 것은 Q0 원점수(안 본 대상 52%)다.

가설인 것:
- **Jev 우선순위를 받은 에이전트가 받지 않은 에이전트보다 같은 예산에서 더 많은 버그에 닿는다.** 이것을 확인하는 에이전트 비교 실험은 아직 하지 않았다. 분명한 차이가 없으면 우선순위 기능을 접고 범위 기록만 남긴다([ADR 0015](docs/adr/0015-agent-harness-direction.md)).
- Jev 2차 재평가가 1차 순위만 쓰는 것보다 나은지는 확인되지 않았다. 지금까지는 반대 신호다(2026-10-01, Magma 버그 38개, 이미 본 대상).
  - 종단 실험의 두 에이전트에서 1차 순서가 나았다.
  - 묶음 전체에 점수를 매기는 방식으로 두 가지 질문을 시험했다. 읽은 유닛 15%에서 1차 25개에 대해 조사 가치 질문 18개, 메모리 안전 판정 질문 9개였다.
  - 판정할 함수를 표시하고 호출 관계 문맥을 붙여도 판별력(AUC)은 함수만 보낸 경우와 같았다(0.687 대 0.682).
  - 문맥을 붙이자 점수가 버그 여부와 상관없이 모두 약 0.02씩 내려갔다. 문맥을 따라가는 판단은 3차 에이전트에게 기대한다.
  - 100줄 넘는 함수를 약 45줄 블록으로 나눠 다시 채점하면 코드 30%에서 25개로, 함수 단위(29개)보다 적었다. 함수로는 낮게 평가되던 아주 긴 버그 함수는 크게 올랐고, 이미 높던 것은 내려갔다. 그래서 둘을 절충하는 방식이 다음 후보다.
- 과거 보안 수정에 맞춘 구성이 새 버그에도 통하는지는 모델과 방법을 먼저 고정한 전향적 판정군으로 확인해야 한다. 연구자에게만 봉인한 공개 사례는 모델에게도 보이지 않았음을 보장하지 않는다([ADR 0021](docs/adr/0021-prospective-cases-for-novel-discovery.md)).
