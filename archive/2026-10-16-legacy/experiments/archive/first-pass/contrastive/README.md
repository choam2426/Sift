# 단일 질문의 대조 판단 실험

Jev 1차 질문을 바꾸면 알려진 취약점으로 이어지는 함수를 같은 선발 예산에서 더 자주 남기는지 확인한다. 이 질문은 한 요청에 `Noul` 하나를 보내지만, 문구 안에서 **정상일 수 있는 설명 → 잘못됐을 수 있는 설명 → 둘을 가를 확인 사항**을 비교하도록 요구한다. 이는 모델 내부 사고 과정을 관측하거나 세 개의 점수를 받는다는 뜻이 아니다.

## 사전 고정 설계

모델은 `jev-1.13.0`, 입력은 함수 전체 본문과 정규화한 함수명, 질문은 [`contrast_holdout.py`](../contrast_holdout.py)의 `contrastive`, `review_worth_plain`, `concrete_suspicion`이다. 비교 질문 두 개는 선행 실험의 문구를 그대로 사용한다. 각 함수·질문 조합을 **독립 요청 세 번** 평가한다. 응답의 `noul` 값으로 내림차순 정렬하고 동점은 유닛 ID 오름차순으로 정한다. 점수는 실제 취약점 확률로 해석하지 않는다.

표본은 [`contrast_holdout.json`](../contrast_holdout.json)에 소스 URL, 전체 파일 SHA-256, 패치와 대응하는 목표 함수를 고정한 여섯 사례다. 각 파일에서 최상위 함수와 클래스 메서드를 **전부** 추출한다. 중첩 함수는 바깥 함수 본문에 포함된다. 클래스 변수·모듈 상수·다른 함수의 본문은 목표 함수 입력에 넣지 않는다. 이는 함수 단위 1차의 맥락 제한을 드러내기 위한 선택이다. 패치 버전의 코드는 Jev에 제공하지 않는다. 이 여섯 사례는 이전 질문 개발에 쓰지 않았으므로 질문 개발 표본과 분리되지만, 공개 취약점 중심으로 선정한 소규모 검증 표본이다. 무작위 코드베이스의 재현율·정밀도를 추정할 수 없다.

| 사례 | 파일 전체 함수 수 | 10% 선발 수 | 35.5% 선발 수 | 목표 함수 | 근거 |
|---|---:|---:|---:|---|---|
| Werkzeug multipart 자원 고갈 | 16 | 2 | 6 | `MultiPartParser.parse` | [유지관리자 공지](https://github.com/pallets/werkzeug/security/advisories/GHSA-xg9f-g7g7-2323) |
| Werkzeug 쿠키 접두사 혼동 | 36 | 4 | 13 | `_cookie_parse_impl` | [유지관리자 공지](https://github.com/pallets/werkzeug/security/advisories/GHSA-px8h-6qxv-m22q) |
| urllib3 303 요청 본문 전파 | 18 | 2 | 7 | `PoolManager.urlopen` | [유지관리자 공지](https://github.com/urllib3/urllib3/security/advisories/GHSA-g4mx-q9vg-27p4) |
| urllib3 압축 스트림 자원 고갈 | 69 | 7 | 25 | `HTTPResponse.read` | [유지관리자 공지](https://github.com/urllib3/urllib3/security/advisories/GHSA-2xpw-w6gg-jr37) |
| Django 여러 파일 검증 우회 | 95 | 10 | 34 | `FileInput.value_from_datadict` | [Django 릴리스 기록](https://docs.djangoproject.com/en/4.2/releases/4.2.1/) |
| Pillow ImageMath 환경 키 실행 | 43 | 5 | 16 | `eval` | [Pillow 릴리스 기록](https://pillow.readthedocs.io/en/stable/releasenotes/10.2.0.html) |

주요 지표는 각 파일의 **상위 10%**에서 목표 함수를 포함한 독립 취약점 기전 수(6개 중 몇 개인가)다. 반올림은 올림을 적용한다. 보조 지표는 선행 실험의 35.5% 예산 결과다. 함수 길이 내림차순과 고정 시드 무작위 선택 1000회도 같은 예산으로 계산한다. 모든 함수의 Jev 평가 성공 여부를 확인하고, 오류가 남으면 그 반복의 도달 수를 산출하지 않는다.

질문을 도입할 만한 강한 신호는 **10%에서 가장 강한 비교 질문 또는 길이 기준보다 독립 기전 두 개 이상을 세 반복 모두 더 찾는 것**으로 미리 정한다. 이 기준을 못 넘으면 문구를 채택하지 않는다. 넘더라도 다른 취약점, 디컴파일 코드, 점수 임계값의 재현성을 별도로 검증해야 한다. 이 실험의 사후 분석으로 질문이나 예산을 바꾸지 않는다.

## 실행

`python3 experiments/first-pass/contrast_holdout.py prepare`로 소스 해시·함수 수·목표 함수 대응을 확인한다. `run --workers 12`는 API 요청당 질문 하나를 보내며, 각 응답을 즉시 Git 제외된 `experiments/first-pass/runs/contrast-holdout/responses.jsonl`에 기록한다. 중단 후 재실행은 입력·질문·모델 해시가 일치하는 성공 건만 건너뛴다. 완료되면 `report`로 순위와 기준선을 출력한다. API 키는 기존 `.env` 또는 환경 변수에서 읽으며 출력하지 않는다.

## 결과

총 277개 함수 × 질문 3개 × 반복 3회 = **2,493건**을 각각 질문 하나의 요청으로 평가했다. 누락·오류 없이 전부 `jev-1.13.0`에서 채점됐고 입력 1,209,306토큰, 출력 57,339토큰을 사용했다. 아래 숫자는 각 반복에서 목표 함수가 예산 안에 든 독립 기전 수다. 모든 비목표 함수의 안전성이 검토된 것은 아니므로 정밀도는 계산하지 않는다.

| 선별 신호 | 상위 10%: 반복 1·2·3 | 상위 35.5%: 반복 1·2·3 |
|---|---:|---:|
| 대조 판단 `contrastive` | **3·3·3/6** | 5·5·6/6 |
| 단순 조사 가치 `review_worth_plain` | **5·5·5/6** | 5·5·5/6 |
| 구체적 오류 의심 `concrete_suspicion` | **3·3·4/6** | 5·5·5/6 |
| 함수 길이 | **4/6** | 5/6 |
| 고정 시드 무작위 1000회 평균 | 0.694/6 | 2.216/6 |

대조 판단 질문은 10% 예산에서 Werkzeug multipart, urllib3 303, Pillow ImageMath 사례를 매번 찾았다. 반면 Werkzeug 쿠키 목표 함수는 36개 중 8위(선발 4개), urllib3 압축 스트림의 `HTTPResponse.read`는 69개 중 19~20위(선발 7개), Django 여러 파일의 `FileInput.value_from_datadict`는 95개 중 32~39위(선발 10개)였다. 단순 조사 가치 질문은 첫 두 함수를 10% 안에 넣어 5/6을 얻었다. Django는 세 질문과 길이 기준이 모두 놓쳤다.

사전 기준인 **최강 기준선보다 세 반복 모두 두 기전 이상 우위**와는 반대 결과다. 따라서 이 문구를 1차 질문으로 채택하지 않는다. 35.5%에서 세 번째 반복의 6/6만 보고 기준을 바꿔서도 안 된다.

질문 내부에서 세 판단을 실제로 수행했는지는 `Noul` 점수만으로 관측할 수 없다. 결과는 이 *문구를 사용했을 때의 순위*만 말해준다. 특히 Django의 취약 동작은 위젯의 다중 파일 설정 및 필드 검증과 함께 봐야 하므로, 3줄짜리 `value_from_datadict` 본문만으로는 단서가 빈약하다. 이 사례를 포함해 세 기전의 미도달이 질문 문구 탓인지 함수 단위 입력의 맥락 부족 탓인지는 분리되지 않았다. 다음 실험을 한다면 동일한 질문과 목표 파일을 유지하고 클래스 선언·직접 호출 계약 등의 맥락만 추가해 이 원인을 분리하는 편이 낫다. 소스 코드만 평가했으므로 디컴파일 코드로 일반화하지 않는다.
