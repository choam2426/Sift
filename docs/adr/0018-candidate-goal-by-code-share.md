# 3차 전 후보 축소 목표는 코드 양 기준 재현율로 정한다

2026-10-01 결정. 1차·2차가 3차 에이전트에 넘기는 후보가 달성해야 할 목표와, 벤치에서 예산을 세는 단위를 정한다.

## 결정

- **예산 단위는 코드 양이다.** 후보가 차지하는 분석 유닛 줄 수를 범위 안 전체 유닛 줄 수로 나눈 비율로 센다. 유닛 개수로 세지 않는다.
- **목표는 코드 양과 재현율의 쌍이다.** 재현율은 벤치 라벨 버그 중 버그 유닛이 하나라도 후보에 든 비율이다.
  - 합격선: 코드 30% 이내에 버그 70% 이상
  - 도전 목표: 코드 10% 이내에 70% 이상, 그리고 30% 이내에 90% 이상
- **판정은 방법을 만들 때 보지 않은 대상에서 한다.** 3차에 넘기는 최종 후보 순서로 재고, 무작위 순서와 긴 함수부터 읽는 순서를 함께 보고한다. 측정 도구는 [`bench/magma/recall.py`](../../bench/magma/recall.py)다.

이 목표는 설계와 벤치의 판정 기준이다. 스펙은 경계만 정하므로 목표치를 스펙에 넣지 않는다. 선별 비율은 지금처럼 파라미터(P-SELECT)로 둔다.

## 이유

**3차 비용은 읽는 코드 양을 따른다.** 유닛 개수로 세면 긴 함수를 고르는 순서가 유리해진다. Magma libpng·libtiff·libxml2(버그 38개)에서 확인한 것:
- 1차 Q0 점수와 로그 함수 길이의 상관은 0.71~0.80이다.
- 버그 함수의 중앙값 길이는 41~65줄로, 전체 중앙값 19~25줄의 2~3배다.
- 그래서 Q0 상위 10% 유닛이 코드의 30~34%를 차지했다.

같은 순서를 두 단위로 세면 결론이 뒤집힌다.

| 순서 | 유닛 10% / 15% / 25% | 코드 10% / 15% / 25% / 30% |
|---|---|---|
| 1차 Q0 | 16 / 25 / 32 | 3 / 9 / 14 / 16 |
| 긴 함수부터 | 13 / 19 / 25 | 2 / 3 / 5 / 9 |
| 무작위 (평균) | 약 비율 × 38 | 5.2 / 7.6 / 12.2 / 14.4 |

유닛 기준에서 Q0는 긴 함수부터보다 나았다. 길이 외의 신호가 조금 있다는 뜻이다. 코드 기준에서는 무작위와 비슷했다.

**결함 예측 연구도 같은 단위를 쓴다.** 노력 인지 결함 예측(effort-aware defect prediction)은 코드 양 일정 비율을 검사했을 때의 결함 재현율(예: Recall@20%)로 평가한다([Mende & Koschke](https://www.researchgate.net/publication/221569956_Effort-Aware_Defect_Prediction_Models), [정의를 다룬 후속 연구](https://arxiv.org/abs/2405.07604)).

같은 착시도 보고됐다. Ostrand, Weyuker, Bell(2005)에서 예측 상위 20% 파일은 결함의 83%를 담았지만, 그 파일들이 코드의 59%였다([논문](https://www.researchgate.net/publication/261170848_Predicting_the_Location_and_Number_of_Faults_in_Large_Software_Systems)). 이 결과는 변경 이력 같은 과정 지표를 썼다.

**목표치는 표준이 아니라 우리의 선택이다.** 2026-10-01에 찾아본 범위에서 이런 목표치를 정한 ISO/IEC 표준은 없었다.
- ISO/IEC 25010·25023은 품질 특성과 측정 방법을 정의할 뿐이다.
- ISO/IEC 5055는 CWE 기반 약점 수를 센다.
- ISO/IEC TS 17961은 C 보안 코딩 규칙을 정한다.

합격선을 30% / 70%로 둔 이유는 무작위(30% / 약 30%)보다 크게 좋아야 3차 전에 좁힐 가치가 있어서다. 이 값은 위 연구들이 보고한 수준보다 높다. 3차를 에이전트가 맡으니 그만큼 좁혀야 한다고 봤다.

## 영향

- 1~5라운드의 Magma 결론("같은 예산에서 Q0를 이긴 방법이 없다")은 유닛 기준 예산으로 잰 것이다. 코드 기준으로 다시 잰다.
- 2026-10-01 현재 어떤 방법도 합격선에 못 미친다. 1차 Q0는 이미 본 대상에서 코드 30%에 42%(16/38)다.
- 같은 날 안 본 Magma 대상(libsndfile·lua·poppler, 버그 44개)에서는 Q0 원점수가 코드 30%에 52%(23/44)로 무작위(30%)보다 나았다. 위 "이유"의 "코드 기준에서는 무작위와 비슷했다"는 이미 본 3개 대상에서만 맞았다. 안 본 대상의 버그 함수가 훨씬 길었기 때문이다. 단위를 코드 양으로 정한 결정은 그대로다. 단위를 바꾸면 성적이 달라진다는 점이 오히려 이 결정의 이유다([실험 요약](../../experiments/README.md)).
- 스펙 P-SELECT의 예시값(유닛 상위 15%)은 합격선을 넘는 방법이 나오면 그 방법의 값으로 바꾼다.

## 재검토 조건

- 3차 에이전트의 비용이 읽는 줄 수에 비례하지 않는다고 확인되면 단위를 다시 정한다. 예를 들어 에이전트가 함수 일부만 읽는 경우다. 토큰 수로 바꾸는 것은 같은 결정으로 본다.
- 안 본 대상에서 합격선이 도달할 수 없는 수준으로 드러나면 목표치를 다시 논의한다.
