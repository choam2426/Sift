# Python·asyncio로 구현하고, C/C++ 함수는 libclang으로 가능한 모든 구성에서 추출한다

2026-09-27 결정. 같은 날 처음에는 코드 조회를 tree-sitter로 시작하기로 했으나, 실제 대상에서 핵심 함수를 놓쳐 아래와 같이 바꿨다.

## 언어와 병렬 처리

Sift는 Python과 `asyncio`로 구현한다. Jev 호출은 I/O 대기이므로 동시성으로 충분하다. 동시 요청 수 제한, 예산 상한, 과금·인증 오류(HTTP 402 등) 시 즉시 정지는 Jev 클라이언트 한 곳에 둔다. 2차 실험의 크레딧 소진은 이 제어가 없어서 생겼다.

C/C++ 파싱은 CPU를 쓰므로 (파일, 구성) 단위로 프로세스 풀에 나눈다. 7-Zip 26.02 `C/`에서 파싱 431회가 1개 프로세스 62초, 10코어(고성능 4개) 19초였다.

재검토 조건: 로컬 분석이 실제 병목으로 측정되면 그 부분만 다른 언어로 옮긴다.

## 코드 조회는 언어별 구현과 공통 인터페이스로 한다

인터페이스는 함수 목록과 **분석하지 못한 코드 목록**이다. 호출자·피호출자·필드 관계는 2차를 만들 때 추가한다.

| 대상 | 구현 | 이유 |
|---|---|---|
| C/C++ | libclang + `compile_commands.json` | 실제 전처리로 매크로를 정확히 처리한다. Apache-2.0이라 비공개 대상에도 쓸 수 있다 |
| C/C++ 추정 | tree-sitter (보정 없음) | 컴파일러가 보지 못한 곳의 정의를 추정해 보고하고, 매크로 켜고 끄기 대상을 고른다. 평가에는 쓰지 않는다 |
| 다른 언어 (이후) | tree-sitter 또는 언어의 공식 파서 | 전처리기가 없어 가벼운 파서로 정확하다. 1차 실험의 Rust·Go·Python 추출이 원문과 일치했다 |

### tree-sitter를 C/C++ 기본으로 쓰지 않는 이유

7-Zip 26.01 `C/`를 Clang 기준 목록과 대조했다. 세미콜론 없는 문장 매크로(`PRF_STR`)로 라벨 함수 `MixCoder_Code`가 580~2877줄로 잡혔다(실제 580~785). 중괄호 짝 맞추기와 매크로 줄 지우기로 보정해도 `Bcj2Dec_Decode`와 Zstd 디코더 4개처럼 첫 프로파일의 핵심 대상이 통째로 빠졌다. 전처리기 없는 파서를 손으로 보정하는 일은 끝이 없어 중단했다.

### CodeQL과 Joern을 쓰지 않는 이유

- **CodeQL:** 7-Zip 643/643, Expat 283/283으로 가장 정확했고 비활성 분기도 정확히 알려준다. 그러나 C/C++ 추출기와 엔진이 비공개 CLI에 있고, 약관상 비공개 코드와 자동 분석에는 유료 라이선스가 필요하다. 라이선스가 있어도 GitHub 밖의 남의 코드가 범위에 드는지 문서로 확인되지 않았다. MIT인 것은 질의·라이브러리뿐이라 그것만으로는 C/C++을 분석할 수 없다. 이 결정으로 [ADR 0006](0006-codeql-source-relation-experiment.md)의 비교 기준 역할도 끝낸다.
- **Joern:** Apache-2.0이고 바이너리(ghidra2cpg)까지 다루지만, `#include`된 `.c` 누락, 코드 1000자 절단, 경로 오류 시 함수 0개로 정상 종료처럼 **누락을 알리지 않는다.** Sift의 범위 기록 원칙과 맞지 않는다. 바이너리 쪽은 이후 따로 다시 본다.
- **ctags, srcML:** 7-Zip 함수의 25% 이상을 오류 없이 누락했다.

## 가능한 모든 구성을 본다

컴파일러는 `#if`의 한쪽만 본다. 7-Zip에서 기준 구성만 쓰면 함수의 약 17%를 못 봤고, 그중에는 `LzmaDec_DecodeReal_3`, `LzmaEnc_CodeOneBlock` 같은 코덱의 대체 구현도 있었다. 그래서 파일마다 다음을 모두 파싱하고 결과를 합친다.

1. compile DB의 구성. compile DB에 없는 소스 파일은 가장 흔한 플래그를 빌려 쓴다.
2. 다른 타깃 4개(x86-64·ARM64·i686 리눅스, x86-64 Windows).
3. tree-sitter가 아직 비활성 줄에서 정의를 찾은 경우, 그 `#if` 조건의 매크로를 켜고(`-D`) 끈(`-U`) 구성. 최대 2회.

3번을 모든 비활성 줄에 적용하면 파싱 1,357회·98초에 함수 914개, 정의가 있는 곳에만 적용하면 431회·17초에 909개였다. 놓친 5개는 tree-sitter가 정의를 찾지 못한 곳이다. **누락이 조용히 일어나지 않도록, 어떤 구성에서도 컴파일되지 않은 줄은 정의로 보이든 아니든 모두 "모든 구성에서 비활성"으로 보고한다.** 5개 모두 이렇게 보고된다. 모든 줄은 어떤 구성에서 컴파일됐거나, 비활성으로 보고됐거나, 어떤 컴파일 단위에도 없는 파일에 속한다.

같은 함수의 시작 줄이 속성 매크로에 따라 구성마다 달라질 수 있어, 함수는 파일과 닫는 중괄호 위치로 식별하고 가장 이른 시작을 쓴다. 매크로가 본문을 만든 함수는 원문에 본문이 없어 "본문이 매크로에서 옴"으로 보고한다. 각 함수에는 그것을 본 구성을 기록한다.

## 시스템 헤더와 플랫폼

libclang만으로는 시스템 헤더 경로를 모르므로 clang 드라이버의 기본 include 경로를 물어 넘긴다. 대상 플랫폼의 헤더는 준비하지 않고 호스트의 헤더를 쓴다. 함수 경계를 깨는 매크로는 대개 프로젝트 자신의 헤더에 있고, 헤더가 없어도 clang은 복구해서 파싱을 계속한다. 파싱 오류 진단 수를 실행 기록에 남겨, 시스템 헤더 의존이 큰 대상에서 문제가 보이면 그때 컨테이너 등을 붙인다.

`compile_commands.json`은 한 번의 빌드나 빌드 없는 추출(`compiledb -n make`, CMake 옵션)로 만든다. 에이전트가 할 수 있는 일이다.

## 재검토 조건

- libclang 바인딩(`clang` 21.x)과 시스템 libclang의 메이저 버전이 다르면 동작을 다시 확인한다.
- 다른 대상에서 비활성으로 보고되는 정의가 많거나 파싱 오류 진단이 크게 늘면 구성 생성 방식을 다시 본다.
- 이 측정은 7-Zip 한 대상이다. `#if`를 적게 쓰는 대상에서는 효과와 비용이 다를 수 있다.
