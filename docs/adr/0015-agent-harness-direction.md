# Sift는 연구원의 에이전트에 붙이는 Jev 우선순위 도구다

> 재검토 상태: 2026-09-29 [ADR 0017](0017-provide-spec-and-materials.md)에 따라 Sift의 제공 형태는 완성된 스킬과 스크립트가 아니라 에이전트가 대상에 맞게 구축할 분석기의 설계·스펙·재료다. 이 문서의 방향은 유지한다.

2026-09-27 결정. Sift는 분석 전체를 수행해 최종 보고서를 내는 도구가 아니라, **연구원이 쓰는 에이전트가 Jev로 효율적으로 우선순위를 정하게 하는 스킬과 스크립트**다. 1·2차 선별과 범위 기록은 Sift가, 심층 분석·검증·판정은 연구원과 에이전트가 맡는다. [ADR 0010](0010-three-stage-structure.md)의 3단계 구조는 유지하되 3차의 실행 주체가 Sift에서 연구원의 에이전트로 바뀐다.

## 이유

- 연구원은 이미 에이전트와 함께 코드를 읽고 가설을 세우고 PoC를 돌린다. 별도 도구보다 그 흐름에 들어가는 편이 쓰인다.
- 3차 심층 분석은 만들기 가장 어렵고 범용 에이전트가 가장 빠르게 좋아지는 영역이다. Sift가 직접 만들면 곧 뒤처진다. Sift는 에이전트가 못 하는 일, 즉 싸고 넓은 Jev 판단으로 어디를 볼지 정하는 일에 집중한다.
- Jev를 쓰는 자리가 늘어난다. 실행 전 전수 선별 외에, 에이전트가 탐색 중 만난 함수 집합(피호출자 수십 개 등)의 순서를 즉시 정하는 용도가 생긴다. 에이전트 스스로는 다 읽으면 비싸고 안 읽으면 놓치는 자리다.
- 실행 환경 제공과 외부 모델 사용 판단은 원래 사용자 책임이었다. 3차를 사용자 에이전트가 하면 모델·비용·데이터 정책을 사용자가 그대로 통제한다.
- 이전 범위(GUI, 무개입 전체 분석, 자체 3차, 동적 검증)는 가치를 보이려면 전부 만들어야 했다. 이제 증명할 것이 하나로 줄었다.

## 무엇이 근거이고 무엇이 가설인가

근거가 있는 것: Jev의 함수 단위 판단은 Python 표본에서 상위 10% 예산으로 6개 기전 중 5개에 도달했고 함수 길이 기준은 4개였다([실험 요약](../../experiments/README.md)). 7-Zip에서는 62.5%가 통과해 변별력이 약했다. 임계값은 모델 버전에 묶여 있다.

가설인 것: 에이전트가 큰 코드베이스에서 어디를 읽을지 정하는 데 약하다는 것, Jev 순위가 에이전트의 싼 휴리스틱(grep, 진입점 추측)보다 낫다는 것, 범위 기록이 연구원에게 가치가 있다는 것. **Jev 우선순위를 받은 에이전트가 실제로 더 효율적인지는 어떤 실험에서도 확인하지 않았다.** 지금까지의 실험은 Jev가 알려진 버그 함수를 상위에 두는지만 봤다.

## 위험과 대응

| 위험 | 대응 |
|---|---|
| 순위의 가치가 증명되지 않음 | Sift를 쓴 에이전트와 쓰지 않은 에이전트를 라벨 사례에서 같은 예산으로 비교하는 것을 첫 실험이자 배포 기준으로 둔다. 분명한 차이가 없으면 우선순위 기능을 접고 범위 기록만 남긴다 |
| 에이전트가 판정을 기록하지 않음 | 배부한 후보와 판정 없는 후보를 Sift가 따로 세어 보고한다. 기록을 강제하지 않는다 |
| 스킬 형식이 에이전트마다 다름 | 계약은 스크립트와 실행 디렉터리 형식이고 스킬은 그 위의 얇은 안내문이다 |
| 외부 모델 하나에 의존 | 모델·질문·임계값 버전을 기록하고 바뀌면 재검토한다 |
| Sift가 순위의 이유를 설명하지 못함 | Jev는 점수만 준다. 한계로 명시한다 |
