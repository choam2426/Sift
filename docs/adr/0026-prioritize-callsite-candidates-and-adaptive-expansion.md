# 2차는 호출지점을 원자로 두고 표현·재순위·확장을 차례로 검증한다

2026-10-03 결정. 첫 C/C++ 메모리 안전성 2차 설계는 소스의 호출지점을 공통 원자로 삼는다. 호출지점별 문맥을 먼저 만들고, 원자를 묶는 경계 정책을 비교한다. 그 뒤 같은 후보에서 Jev 재순위의 기여를 확인하고, 마지막으로 고정 확장과 적응형 확장을 비교한다.

큰 관련 코드 묶음 전체에 점수 하나를 주는 기존 A·B·D·E 방식은 새 실행 조건에서 제외하고 기각 근거와 비교 자료로만 보존한다.

## 근거

기존 큰 묶음 실험에서는 묶음 점수가 크기와 상관했고, 함수 단위 1차보다 같은 코드 예산에서 적은 버그에 닿았다. 판정할 `TARGET`을 표시한 8,000토큰 이하 문맥도 함수만 보낸 대조군 대비 AUC 차이가 +0.005였고 95% 구간은 −0.036~+0.045였다. 긴 함수를 약 45줄 블록으로 나눈 방식도 코드 30% 예산에서 함수 단위보다 적은 버그에 닿았다. 작은 문맥이 Jev의 관계 판단을 개선한다는 근거는 아직 없다.

CyberGym `arvo:10400` 파일럿의 `ReadMNGImage`에는 직접 피호출자가 40개 있다. 패치 대상 `mng_get_long`은 그중 하나이며 24개 호출지점에서 직접 호출된다. 이 사례는 관련 함수를 시작 패킷에 넣을 필요성을 보여주지만, Jev가 그 관계를 재평가하면 순위가 개선된다는 증거는 아니다. 이 과제는 설계를 만든 개발 사례로만 사용한다.

## 공통 원자

원자 ID는 호출 원문의 위치와 표현을 중심으로 만든다. 실행 기록의 리비전, 파일, 원문·확장 위치, 소스 범위와 호출 표현 해시로 같은 스냅샷의 호출지점을 식별한다. caller, 구성별로 해석된 callee와 호출 종류는 속성으로 둔다. 빌드 구성에 따라 callee 해석이 바뀌어도 원문 호출의 정체성은 유지한다.

각 원자는 다음을 기록한다.

- 호출 원문과 소스 범위
- caller와 구성별 callee 해석
- 매크로 원문·확장 위치
- 인자와 결과 표현
- 포함한 문맥과 그 출처
- 계산하지 못한 alias·간접 호출·정의와 다른 생략 관계

문맥을 계산하지 못한 호출지점을 안전하거나 조사 가치가 낮다고 간주하지 않는다.

## 문맥 조건

병합 전에 각 호출지점에 같은 규칙을 적용한다.

- **M0 최소 문맥:** 호출 표현, 필요한 시그니처와 선언, callee 본문, 호출 결과를 받는 표현
- **M1 관련 문맥:** M0에 계산 가능한 도달 정의, 호출 도달 여부에 영향을 주는 조건, 인자·결과의 데이터 흐름, 관련 검사·산술·형변환·사용을 원래 순서와 분기 구조를 보존해 추가
- **MX 크기 대조:** M0에 M1과 같은 토큰 수의 코드를 추가하되, 추출기가 해당 호출과의 데이터·제어 의존성을 발견하지 못한 코드에서 결정적으로 표집

M1과 MX의 관계 판정은 완전하다고 주장하지 않는다. 포함 근거, 표집 규칙과 찾지 못한 관계를 기록한다. M1은 M0와 MX를 모두 이겨야 관련 문맥의 효과가 있다고 본다.

## 경계 정책

호출지점별 문맥을 만든 뒤 다음 정책으로 원자와 문맥을 결정적으로 병합한다.

- **C 개별 호출지점:** 원자 하나가 후보 하나다.
- **R 제어영역:** caller와 callee가 같고 같은 가장 안쪽의 어휘적 분기·루프 arm에 있는 원자를 묶는다. 감싸는 영역이 없으면 개별 호출지점으로 둔다.
- **P caller-callee:** 같은 caller-callee의 모든 원자를 묶는다.

후보 ID는 경계 정책과 정렬된 구성원 원자 ID로 만든다. 병합한 코드의 중복은 소스 범위로 제거하지만, 모델에 실제로 다시 보낸 토큰은 비용에서 제거하지 않는다. 입력 한도를 넘긴 후보는 임의로 자르지 않고 미평가와 이유를 기록한다.

R은 지역 검사와 호출을 싸게 함께 담을 수 있다는 선두 가설이다. 의미적인 데이터·제어 경계라고 가정하지 않는다. P·R·C는 동등한 비교 조건이며 실험 전에는 기본값을 고정하지 않는다.

## 게이트 1: 경계와 문맥

개발군에서 먼저 `P-M1`, `R-M1`, `C-M1`을 비교한다. 주 결과는 실제 누적 비용 안에서 충분한 근거에 도달한 고유 결함 수다. 호출지점 수를 결함 수로 세지 않는다. 요청 수, 실제 입력·출력 토큰, 추출 시간, 입력 한도 초과와 에이전트 비용을 함께 보고한다.

전수 구조 목록은 모델 호출 없이 만든다. P·R·C의 구성원 원자 집합이 같은 후보는 상태 해시로 한 번만 평가한다. 호출지점 하나뿐인 P 그룹은 세 정책의 경계 차이를 알려주지 않으므로 경계 선택 표본에서 제외한다.

경계 선택은 다중 호출 P 그룹에서 다음 순서로 진행한다.

1. 개발 라벨의 필수 근거와 연결된 그룹을 모두 포함한다. 이 포함 목록은 후보 생성 뒤 평가기가 적용하며 Jev 입력에는 주지 않는다.
2. 호출 수, 입력 크기, R 분할 수, 1차 점수를 기준으로 결정적으로 층화한 200개 그룹에서 세 정책을 비교한다.
3. 명백한 열세 정책을 중단하고, 남은 정책을 앞의 표본을 포함하는 누적 800개 그룹까지 확대한다.
4. 우승 정책만 전수 후보에서 실행한다.

200·800 비교는 개발용 선택 절차다. 표본 밖의 일반 성능이나 우월성을 주장하지 않는다. 우승 정책의 전수 실행과 별도 평가군이 최종 근거다.

우승 경계를 `W`라고 하고 같은 개발 표본에 `W-M0`, `W-MX`를 추가한다. 첫 탐색은 다음 다섯 조건이다.

1. P-M1
2. R-M1
3. C-M1
4. W-M0
5. W-MX

이 다섯 조건은 M1에서의 경계 선택과 선택된 경계에서의 문맥 효과만 설명한다. P·R·C 전체의 경계-문맥 상호작용을 주장하지 않는다. 결과가 애매하거나 상호작용을 확인할 필요가 생기면 3×3 전체 조건으로 확대한다. 개발군에서 선택한 구성의 일반 성능은 구성을 고정한 뒤 별도 평가군에서 확인한다.

R의 취약성을 보기 위해 `if (true)` 감싸기, guard clause와 `else` 사이 변환, 독립 문장 순서 변경을 작은 표본에 적용한다. 의미를 보존한 변환 전후의 후보 구성원, 후보 수와 순위 변화를 진단 결과로 보고한다.

## 게이트 2: Jev 재순위

게이트 1에서 고른 후보 패킷을 고정하고 다음 순서를 비교한다.

- 1차 점수와 안정적인 후보 ID로 만든 기존 순서
- 2차 Jev 점수로 만든 순서
- 무작위 순서 진단군

후보 내용, 에이전트, 조사 예산은 같게 둔다. Jev 순서가 기존 순서보다 같은 조사 예산에서 더 많은 고유 결함과 독립 검증된 PoC에 도달해야 2차 Jev 호출의 추가 가치를 인정한다. 효율성에는 후보 생성과 2차 Jev 비용을 포함한다.

## 게이트 3: 확장 정책

게이트 2를 통과한 표현과 순위를 고정하고 다음을 비교한다.

- **고정 확장:** 모든 후보에 같은 단계의 문맥을 추가한다.
- **적응형 확장:** 모든 후보를 같은 기본 상태로 평가한 뒤, 결정적인 우선순위와 고정 예산에 따라 일부 후보만 확장한다.

적응형 조건은 다음을 지킨다.

- 사전에 고정한 유한한 확장 단계만 사용한다.
- 모든 후보에 같은 기본 평가를 적용한다.
- 후보별 확장 횟수와 비용 상한을 같게 둔다.
- 동점은 안정적인 후보 ID로 해결한다.
- 단계별 최고 점수를 최종 점수로 사용하지 않는다.
- 문맥 단계가 다른 점수의 결합 규칙을 개발군에서 미리 고정한다.
- 다음 확장이 입력 한도나 잔여 예산을 넘으면 이유와 미평가 frontier를 기록한다.
- 고정 예산, 후보 소진 또는 공통 오류 규칙에서 멈춘다.

고정 순회 확장은 필수 대조군이다. 높은 점수만 확장하는 정책은 문맥 부족으로 낮게 평가된 후보를 영구히 제외할 수 있으므로, 점수가 추가 문맥의 가치를 나타낸다는 근거 없이 기본값으로 사용하지 않는다.

## 라벨과 평가

개발용 결함 라벨에는 결함 ID, 필요한 근거, 대체 가능한 근거 집합, 문제가 되는 호출 경로와 독립 PoC 조건을 둔다. 후보 생성기와 Jev에는 라벨을 주지 않고 평가기만 후보가 충분한 근거를 제공하는지 판정한다. 취약한 callee를 호출한다는 이유만으로 모든 호출지점을 양성으로 세지 않는다.

- 불확실성은 호출 수가 아니라 결함과 프로젝트 단위로 계산한다.
- 알려진 라벨이 없는 후보와 검토해 문제가 없다고 확인한 후보를 구분한다.
- 주 비용 축을 실행 전에 고르고 요청 수, 입력·출력 토큰, 추출·실행 시간과 에이전트 사용량을 모두 보고한다.
- 성능 차이가 불분명하면 우월성이나 비열등성을 주장하지 않는다. 탐색용 선택을 했다면 그 사실과 공학적 동률 처리 규칙을 기록한다.
- 오프라인 점수만으로 채택하지 않는다. 비용 대비 근거 도달과 동일 에이전트·예산·독립 PoC 검증의 종단 성과를 함께 본다.

## 범위와 아직 정하지 않은 값

첫 구현과 결론은 C/C++에서 정적으로 해석한 지원 호출 관계에 한정한다. 외부·간접 호출, 매크로와 구성별 해석 실패를 범위 보고에 남긴다. 이 결과만으로 다른 언어나 호출 관계가 없는 결함까지 일반화하지 않는다.

다음 값은 각 실행 전에 개발군에서 고정한다.

- M1의 정확한 관계 추출 범위와 MX 표집 규칙
- 첫 2차 질문과 응답 결합 방식
- 경계 선택의 주 비용 축, 실용적 개선 폭과 동률 처리
- 확장 단계와 frontier 우선순위
- 후보별 한도와 전체 토큰·요청·시간 예산
- 1차 점수, 2차 점수와 후보 중복을 최종 순서로 합치는 방법

연구자에게만 봉인한 공개 사례는 모델의 비공개 판정군으로 취급하지 않는다.
