# ADR 0005: 학습 기준일 이후 사례의 이미지는 고정 소스로 직접 빌드한다

- 날짜: 2026-10-16
- 상태: C/C++ testbed 방법으로 보존. 활성 실험은 [ADR 0006](0006-logic-bug-ranker-experiment.md)을 따른다.
- 관련: [ADR 0001](0001-jev-collaboration-research-charter.md), [ADR 0002](0002-cybergym-images-as-shared-testbed.md), [ADR 0004](0004-measurement-cases-after-training-cutoff.md)

## 맥락

ADR 0004는 측정·비교 사례를 모델 학습 기준일 이후에 수정·공개된 취약점에서 고르라고 정했다. CyberGym의 사전 빌드 이미지는 모두 그 이전 사례이고, ARVO의 최신 이미지도 2026-02-19 갱신이라 2026년 7~9월 사례가 없다. ARVO 파이프라인은 Google Cloud 자격 증명과 전체 DB를 요구하고, OSS-Fuzz의 `helper.py`는 현재 HEAD를 빌드하므로 취약 리비전이 아니다.

2026-10-16에 md4c(OSV-2026-1274)로 고정 소스 빌드를 실제로 검증했다. 공개 OSS-Fuzz 이슈에서 참조 테스트케이스를 받을 수 있었고, 취약 리비전과 수정 리비전을 각각 빌드해 같은 입력으로 취약판 크래시·수정판 비크래시를 확인했다.

## 결정

1. **사례 레시피를 고정한다.** 사례마다 프로젝트 저장소, 취약 리비전, 수정 리비전, OSS-Fuzz 프로젝트 레시피 리비전, `base-builder` 이미지 digest, 퍼징 하네스, 참조 테스트케이스 URL과 SHA-256, 기대 크래시 서명(유형·파일·줄·함수)을 기록한다.
2. **두 이미지를 같은 빌드 스크립트로 빌드한다.** 소스는 `git archive`로 꺼내 `.git`을 넣지 않고, 빌드 중 네트워크를 쓰지 않으며, `base-builder` digest와 레시피 리비전을 고정한다. 빌드 컨텍스트·명령·로그·해시를 번들에 남긴다.
3. **참조 테스트케이스로 판정을 검증한다.** 취약판은 2회 모두 기대한 ASan 서명으로 크래시해야 하고, 수정판은 2회 모두 하네스가 실제로 입력을 실행하고 크래시 없이 끝나야 한다. 종료 코드만 보지 않는다.
4. **취약 이미지는 깨끗한 로컬 이미지로 쓴다.** 소스에 `.git`이 없고 참조 입력·패치가 이미지에 없다. 수정 이미지는 `fix.tar`로 저장한 뒤 Docker에서 제거하고, `evaluate`·`run`이 평가할 때만 불러와 ID를 확인하고 끝나면 다시 제거한다. `preflight`는 수정 이미지가 로드돼 있거나 아카이브가 없으면 실패한다.
5. **정체성은 내용 키로 둔다.** 이미지 이름은 고정 입력(저장소·커밋·레시피·베이스 digest·빌드 스크립트 해시)의 내용 키에서 파생하고, 실제 이미지 ID는 빌드 산출물로 기록한다. 태그나 ID를 사례 입력으로 쓰지 않는다.
6. **사례 선정은 결과를 보기 전에 고정한다.** 후보 풀, 제외 이유, 모델별 기준일, 참조 테스트케이스 부재 시 제외, OSV 도입 커밋이 재현되지 않을 때의 대체 규칙을 실행 전에 기록한다. 참조 테스트케이스가 없거나 재현되는 취약 리비전을 찾지 못하면 그 사례는 측정에서 제외한다.
7. **기대 서명으로 같은 결함을 확인한다.** 한 사례의 취약·수정 구간에 여러 수정이 섞여 있을 수 있으므로, 기대 ASan 서명이 일치하지 않는 크래시는 `reproduced`가 아니다.
8. **의존성도 고정한다.** 레시피의 `dependencies`에 이름·저장소·커밋·프로젝트 안 목적 경로를 기록하고, 의존성 소스도 `git archive`로 꺼내 `.git` 없이 빌드 문맥에 넣는다. libzip은 zlib v1.3.1을 이 방식으로 쓴다. 의존성의 빌드 방법은 사례별 빌드 스크립트에 둔다.

## 번들

```
<bundle>/
  case.json      로컬 이미지 참조, 기대 크래시, 참조 해시
  build.json     고정 입력, 전체 명령·로그 경로, 이미지 ID, 검증 결과, 감사, 하네스 바이너리 해시, clang/cmake 버전, 빌더 스크립트 해시
  reference.bin  참조 테스트케이스 (control 자료)
  fix.tar        수정 이미지. 빌드 후 Docker에서 제거됨
  logs/          빌드·실행 전체 로그
```

`testbed/build_case.py build <recipe> --out <bundle>`가 번들을 만들고, `testbed.py preflight|prepare|selfcheck|evaluate|run`이 번들의 `case.json`을 받는다. 에이전트 작업 공간은 번들과 분리되고 `control/`은 읽기 금지된다.

## 검증 근거 (md4c, OSV-2026-1274 / OSS-Fuzz 560657993)

- 참조 테스트케이스 3,062바이트, SHA-256 `79dd4d97...`.
- 취약 `10fa4f4`: 2회 모두 `heap-buffer-overflow`, `/src/md4c/src/md4c.c:3409` `md_collect_marks`.
- 수정 `60965ab`: 2회 모두 하네스 실행, 크래시 없음.
- 수정 커밋의 직계 부모 `be74ea1`: 같은 테스트케이스에서 크래시 없음. 따라서 "취약 = 수정 부모" 규칙은 쓰지 않고, 참조 테스트케이스로 재현되는 리비전을 기록한다.
- 같은 빌드 스크립트로 두 이미지를 빌드했고, 모두 `.git`과 `/tmp/poc`이 없으며 이미지 히스토리에 참조 URL·해시가 없다.
- 빌드: 콜드 약 19초, 캐시 적중 약 1초. 이미지 3.03GB, `fix.tar` 735MB.
- `preflight`와 `selfcheck` 통과, 평가 중에만 수정 이미지가 로드되고 끝나면 제거됨.

## 기각한 대안

- **ARVO 파이프라인**: gcloud 자격 증명과 전체 DB가 필요하고, 2026년 사례 이미지가 없다.
- **ARVO 이미지 대기**: 제공 시점을 알 수 없다.
- **OSS-Fuzz `helper.py` 그대로**: 현재 HEAD를 빌드해 취약 리비전이 아니다.
- **CyberGym 사전 빌드 이미지**: 모두 학습 기준일 이전 사례다.

## 한계

- 참조 테스트케이스가 공개되지 않은 사례에는 이 방법을 쓸 수 없다. 직접 퍼징으로 대체하지 않고 측정에서 제외한다.
- 빌드 레시피의 의존성은 사례마다 다르다. `dependencies`에 저장소·커밋·목적 경로를 고정하고, 의존성도 `git archive`로 꺼내 `.git` 없이 넣는다. libzip은 zlib v1.3.1을 이 방식으로 쓴다. `base-builder` digest는 고정했지만 그 안의 패키지 버전은 고정되지 않는다.
- 이미지는 로컬에 있고, 수정 이미지는 `fix.tar`로만 보관한다. 호스트 디스크와 Docker 소켓 경로는 여전히 신뢰 경계다.
- 한 사례의 취약·수정 구간에 여러 결함이 있을 수 있다. 기대 서명이 이를 걸러내지만, 서명이 같은 다른 경로는 구분하지 못한다.
- TASK.md는 판정 하네스를 지목한다. 조사 범위를 정하는 정보이며 결함 위치가 아니지만, 사례마다 같은 방식으로 제공해야 한다. 하네스 이름이 주는 정보 우위는 사례 간 비교에 기록한다.
- 세 조건의 예산 분할과 Jev 호출 회계는 이 ADR의 범위가 아니다. ADR 0001·0003의 후속 설계에서 정한다.
- 측정 사례는 [ADR 0004](0004-measurement-cases-after-training-cutoff.md)에서 세 건을 선정했다. md4c는 방법 검증용이며 측정 사례가 아니다.

## 재검토 조건

사례를 추가·교체할 때, 의존성 고정 방식을 바꿀 때, 모델 기준일이 바뀔 때, 전향적 평가를 설계할 때.
