# ADR 0010: Phase 2 — 심은 인가 결함으로 탐색 비용 가설을 검증한다

- 날짜: 2026-11-08
- 상태: **진행 중.** 사례 생성 절차와 seed는 이 ADR과 함께 커밋해 고정했다. 사전 선별은 순위 계산과 실행 전에 마쳤다([선별 기록](../../experiments/planted/screening.md)). 범위 문구·비용 상한·반복 수는 §6의 파일럿 규칙으로 정한 뒤 본 실험 전에 이 문서에 추가한다.
- 관련: [ADR 0009](0009-conclude-research-after-stage-0.md)(Phase 1 결론), [제품 결정 메모](../jev-package-decision-memo.md)

## 맥락

[ADR 0009](0009-conclude-research-after-stage-0.md)는 개발 사례 4개로 다음 탐색적 결론을 냈다. **Jev 탐색 보조는 탐색이 긴 문제에서 비용을 줄였고, 짧은 문제에서는 overhead였다.** 연구자는 2026-11-08 후속 연구 진행을 위임했다. 이 ADR은 그 결론을 독립 사례로 검증하는 Phase 2다. Phase 1의 결론은 바꾸지 않는다.

ADR 0009가 남긴 걸림돌은 세 가지다.

1. **사례 공급.** 학습 기준일(2026-06-30) 이후 수정된 Go 인가 결함 중 기준을 통과한 것은 OpenList 하나였다. 2026-11-08에 다시 확인했다. Gitea advisory 6건(수정 2026-02-20~06-22)과 Coder advisory 1건(2026-06-09)은 공개만 7월 이후였고, 수정은 모두 기준일 이전이었다.
2. **Jev ranking의 증분 효과.** Phase 1은 Jev 순위가 "순위 목록이 있다는 것" 이상의 가치를 주는지 분리하지 못했다.
3. **조절 변수의 측정 방식.** Phase 1의 "vanilla 턴이 길수록 이득이 크다"는 같은 vanilla 실행을 x축(턴 수)과 비율의 분모에 함께 썼다. vanilla가 우연히 길게 나온 사례는 비율도 우연히 작아지므로, 효과가 없어도 음의 상관이 생긴다. 이 관측은 가설로만 남긴다.

## 결정

### 1. 결함을 규칙으로 심어 사례를 만든다

학습 기준일 이후 리비전에 인가 결함을 하나 심는다. 결함은 새로 만든 것이므로 모델이 학습했을 수 없다.

- **변이 연산자**(`experiments/planted/plant/`):
  - `guard-delete`: 거부하는 인가 guard(`if !CanWrite(...) { deny; return }`)를 지운다.
  - `middleware-delete`: route 등록에서 인가 middleware 인자 하나를 지운다.
  - `cond-weaken`: 거부 조건 `a || b`에서 인가 항 하나를 지운다.
  - `scope-delete`: 조회 옵션에서 호출자 범위 필드(`OwnerID: doer.ID` 등)를 지운다.
  - 바로 위 주석과 남는 빈 줄을 함께 정리하고 gofmt를 적용한다. 그 결과 diff가 원래 코드처럼 보인다.
- **후보 나열**: AST와 이름 규칙으로 후보를 모두 나열한다. test·mock·testdata·생성 파일·`cmd/`·migration은 제외한다.
- **kill 필터**(`experiments/planted/pool.py`): 같은 패키지의 기존 테스트 중 원본에서 통과하고 변이에서 실패하는 것이 있어야 한다. 이 조건이 결함의 실재성(비등가 변이)과 테스트 가능성을 보장한다.
  - 패키지 밖 통합 테스트로만 잡히는 변이(예: Gitea의 route middleware 대부분)는 제외된다. 이 편향은 한계로 기록한다.
- **무작위 선택**: 저장소별로 seed(`repos.json`의 `seed`와 저장소 id)로 후보 순서를 섞고, 그 순서대로 kill을 판정한다. 먼저 kill된 순서가 곧 kill된 집합의 무작위 표본이다.
- **사전 선별**: 실행 전, 결과를 보기 전에 kill된 후보를 순서대로 다음 기준으로 거른다.
  - 지워진 코드가 "누가 어떤 자원에 무엇을 할 수 있는가"를 결정한다.
  - 그 경로가 권한이 낮거나 신뢰할 수 없는 호출자에게 닿는다.
  - 탈락하면 다음 순서로 넘어간다. 탈락 사유는 모두 기록한다.
- **에이전트 트리**: 변이를 적용하고, 변이에서 실패하는 기존 테스트 함수를 지운다. 그러지 않으면 테스트 실패가 위치 힌트가 된다. 평가에 쓰는 수정판은 같은 테스트를 지운 원본이다. 두 트리의 차이는 심은 결함 하나뿐이다.

#### 실행 전 보완 (2026-11-08, 사례 실행 전)

후보를 실제로 보면서 다음을 정했다. 모두 어떤 사례도 실행하기 전, 순위를 계산하기 전에 정했다.

- **선별 기준을 구체화했다.**
  - fail-open이어야 한다. 정상 요청을 실패시키거나 nil 역참조를 일으키는 변이는 제외한다.
  - 관리자 설정 한도·정책(생성 한도, 허용 목록)은 인가 결정으로 보지 않는다.
  - 서버 관리자나 내부 서비스 신원만 닿는 경로는 제외한다.
  - 같은 저장소에서 이미 고른 사례(파일럿 포함)와 같은 파일의 후보는 건너뛴다.
  - 저장소의 kill 후보가 바닥나면 그 저장소는 고른 만큼만 쓴다.
- **변이 검사를 전이 의존까지 넓혔다.** 변이 패키지에 직접·간접으로 의존하는 테스트 패키지에서 변이에만 실패하는 테스트를 두 트리 모두에서 지운다. 같은 최상위 디렉터리를 먼저 보고 최대 60개 패키지를 검사한다. 그러지 않으면 에이전트가 테스트를 넓게 돌릴 때 기존 테스트 실패가 위치 힌트가 된다.
- **평가기가 testify suite 메서드를 인식한다.** 최상위 `TestXxx` 함수와 suite 메서드를 각각 선택해 실행하고, `go test -json`으로 제출 테스트 각각의 결과를 본다. Gotify·Authelia·Grafana는 suite를 많이 쓴다. Phase 1 평가기는 최상위 함수만 인식했다.
- **선별 결과**: 본 실험 13개(Authelia 1개, 나머지 저장소 2개씩)와 파일럿 3개. 사유는 [선별 기록](../../experiments/planted/screening.md)에 있다.
- **변이가 빈 블록을 남기지 않는다.** guard를 지워 감싸는 `if`가 비면 그 `if`도 지운다. 조건에 호출이 없고 `else`·init이 없을 때만이다. 빈 `if cond {}`는 실제 결함에는 없는 단서다. 선택된 16개 중 Argo CD 파일럿만 해당했고, 후보 목록은 바뀌지 않았다.
- **테스트 잔여물을 지운다.** 사례 트리에서 테스트를 돌린 뒤, 원본에 없는 파일(예: Argo CD `reposerver`의 `testdata/` 임시 디렉터리)을 지운다.
- **변이의 흔적을 메타데이터에서 지운다.** 파일럿 첫 3회(Argo CD vanilla·rank-jev, Grafana vanilla)의 에이전트가 모두 파일을 mtime으로 정렬했다(`find -printf '%T@'`, `find -newer go.mod`). 변이 파일과 테스트를 지운 파일만 더 새로웠기 때문에 위치가 드러났다. Grafana vanilla는 이 단서로 26턴 만에 끝났다. **이 3회는 무효**로 하고 파일럿을 처음부터 다시 한다. 대응은 다음과 같다.
  - 에이전트 소스의 모든 파일·디렉터리에 같은 고정 mtime을 준다.
  - 에이전트 빌드 캐시는 사례 트리의 `go build ./...`로 처음부터 만든다. 테스트 패키지는 미리 컴파일하지 않는다. 그러지 않으면 `go list -test`의 stale 여부나 패키지별 캐시 항목 수로 변이 패키지가 드러난다. 캐시 항목에도 prepare 시점의 같은 mtime을 준다.
  - 테스트를 지울 때, 지운 테스트만 쓰던 unexported helper도 지운다. 남은 미사용 helper는 제거된 동작을 가리킨다.
  - 확장 속성(xattr)·권한은 변이 파일과 나머지가 같음을 확인했다.
  - Phase 1에서도 에이전트가 mtime을 본 실행이 있었다(Pocket ID route-index). 하지만 Phase 1 소스는 실제 리비전 아카이브라 모든 파일의 mtime이 같아 단서가 없었다.
- **주 지표는 상한에서 censoring한 비용이다 (2026-11-09 정정).** 파일럿 Gitea vanilla는 발견 없이 $23.79에서 스스로 멈추었다. §5 H1의 "실패 실행 포함 비용"을 실제 비용 평균으로 계산하면, 일찍 포기하는 arm이 싸 보인다. 그래서 이 프로젝트의 원래 주 지표로 되돌린다([ADR 0007](0007-three-arm-ranker-evaluation-after-independent-review.md) 결정 4). valid 실행은 전체 비용, 아닌 실행은 상한을 비용으로 친다. 실제 비용 평균은 보조 지표로 보고한다. 본 실행 전, 본 실험 결과를 보기 전에 고쳤다.
- **의존 패키지 검사에서 `test`·`tests` 디렉터리도 제외한다.** Grafana `pkg/tests/...`는 서버 전체를 띄우는 통합 테스트다. 패키지 하나가 제한 시간(900초)을 넘겨, 라운드마다 일부 테스트만 끝났다. 그 바람에 Grafana 본 사례 2개가 3라운드 안에 수렴하지 못했다. `plant`가 후보에서 제외하는 디렉터리와 같은 기준이다. 에이전트가 이 패키지를 직접 돌리면 지우지 않은 테스트 실패가 힌트가 될 수 있다. 그래서 broker 기록으로 그런 실행이 있었는지 집계한다. 이미 만든 사례는 더 넓게 검사됐으므로 다시 만들지 않는다.
- **본 실험 순서를 seed로 고정한다.** `queue.py`는 반복마다 모든 (사례, arm)을 한 번씩 담은 블록을 만든다. 블록 안 순서는 seed로 섞는다. 며칠에 걸친 실행 동안의 시간 효과(모델·서비스 변화)가 arm에 고르게 퍼진다. 사례 빌드처럼 CPU·메모리를 많이 쓰는 작업은 에이전트 실행과 동시에 돌리지 않는다.
- **인프라 중단은 다시 실행한다.** 실행이 세션 한도 등 API 오류(`terminal_reason: api_error`)로 끝나면 `infra_abort`로 표시한다. 제출물이 있어도 평가·분석에서 빼고, 한도가 풀린 뒤 같은 조건으로 다시 실행한다. 비용 상한 도달(`budget_exhausted`)은 에이전트의 결과로 집계한다. 이 규칙을 정하다가 Phase 1 Stage 0의 Arcane vanilla r2가 결함 제출 뒤 한도에 걸려 끝난 것을 발견했다. 비용이 약간 과소추정되었을 수 있어 `results/runs.csv`에 표시했다.

### 3. 비교: 3-arm, 순위의 출처를 가린다

| arm | 받는 것 |
| --- | --- |
| `vanilla` | 소스, 과제, `./tb` |
| `rank-bm25` | vanilla + file 단위 unit index + **BM25 순위** |
| `rank-jev` | vanilla + 같은 unit index + **Jev 순위** |

- `rank-jev` vs `vanilla`는 제품 효과다. Phase 1 Stage 0의 재현이다.
- `rank-jev` vs `rank-bm25`는 Jev 순위 내용의 증분 효과다. 둘은 같은 형식의 순위 목록을 받는다. 그래서 "순위 목록이 있다는 것" 자체의 효과가 상쇄된다.
- **순위 출처를 가린다.** 두 arm의 안내문은 같고 "자동 ranker"라고만 쓴다. 점수 척도가 출처를 드러내므로 점수는 보여 주지 않고 순위만 준다.
- **순위는 미리 계산한다.** Phase 1 Stage 0에서 Jev arm 12회는 모두 `./jev rank`를 정확히 한 번 실행했고 `ask`는 쓰지 않았다. 순위를 harness가 준비 단계에서 계산해 주면 에이전트가 받는 정보는 같다. 대신 대기 시간과 실행 여부의 변동이 없어진다. Jev는 실행마다 새로 호출하고, 그 비용과 시간을 해당 실행에 포함한다.
- **질문은 모든 사례에 하나다.** Phase 1은 결함을 아는 사람이 사례별 질문을 썼다. Phase 2는 Phase 1의 가장 일반적인 질문(Kite)에서 "route"를 "code"로만 바꿔 고정한다. 순위 방향(Noul 높은 순)과 Jev 모델(`jev-1.14.0`)도 Stage 0과 같다.

> Does this code enforce the caller's authorization for the resource and context it actually operates on before the protected operation?

### 4. 실행 경계와 평가기

- **broker**: 에이전트는 Docker 소켓에 접근하지 못한다. `./tb test|build|exec`는 workspace 밖 Unix socket의 broker에 요청한다. broker가 그 요청만 컨테이너에서 실행하고 모두 기록한다. Phase 1 Vikunja r2의 경계 위반이 막힌다. 에이전트 컨테이너의 모듈 캐시는 읽기 전용이다.
- **테스트 위치는 에이전트가 정한다.** Phase 1 과제는 테스트 패키지를 알려 줬다. 그것이 위치 힌트였다. Phase 2 에이전트는 `findings/<name>/package.txt`에 테스트를 놓을 디렉터리를 적는다.
- **기술 판정**: Phase 1과 같다. 취약판에서 3회 모두 실패하고, 수정판에서 3회 모두 통과하고, decoy에서 3회 모두 실패해야 한다.
- **유효(valid)**: 다음을 모두 만족해야 한다.
  - 기술 판정 통과
  - 감사 위반 없음(Docker·네트워크·subagent)
  - 비용 상한 이내
  - `report.md`가 심은 파일을 지목
  - 테스트가 `.go` 소스를 읽어 판정하지 않음

  모두 자동으로 판정한다. Phase 1의 비맹검 수동 의미 검토를 대체한다.

### 5. 가설, 예측, 분석

사례 = 심은 결함 하나. 본 실험은 저장소당 2개를 목표로 했고, 선별 결과 13개다. 반복 수는 §6에서 정한다.

- **H1(제품 효과)**: `rank-jev`의 전체 비용(Claude + Jev, 실패 실행 포함)은 `vanilla`보다 낮다.
  - 지표: 사례별 arm 평균 비용 비율의 기하평균. Stage 0의 주 지표와 같다.
  - 예측: < 0.90
- **H2(Jev 순위의 증분)**: `rank-jev`는 `rank-bm25`보다 낮다.
  - 예측: < 0.95
- **H3(조절)**: log 비용 비율(`rank-jev`/`vanilla`)은 저장소 크기(파일 unit 수의 log)가 클수록 작다.
  - 크기는 실행 전에 정해진다. 그래서 §맥락 3의 결합 문제가 없다.
  - 예측: 기울기 < 0. 대형(Gitea·Grafana)의 비율 ≤ 0.80, 소형은 ≈ 1.0.
- **판정 규칙**:
  - 비율 추정치는 저장소 단위로 묶은 bootstrap 95% CI로 보고한다.
  - H1·H2는 다음과 같이 판정한다.
    - 지지: 점추정이 예측 범위 안이고 CI 상한 < 1.0
    - 반박: 점추정 ≥ 1.0
    - 나머지: 결론 보류
  - H3는 저장소가 7개라 기울기 추정과 CI만 보고한다. 확증 검정으로 쓰지 않는다.
- **보조 지표**: valid 비율, 턴, wall time, 심은 파일을 처음 연 턴, 심은 파일의 Jev·BM25 순위(변이판·원본)

### 6. 파일럿: 실행 가능성만 보고, 본 실험에 쓰지 않는다

- 대형 2개(Gitea, Grafana)와 중형 1개(Argo CD)에서 저장소별 첫 선별 통과 결함을 파일럿용으로 쓴다. 본 실험에는 다음 순서의 결함을 쓴다.
- 파일럿에서 `vanilla`·`rank-jev`를 1회씩 실행한다. 범위는 "이 저장소 전체의 인가 결함", 상한은 $30.
- **범위 결정 규칙**: 파일럿 `vanilla` 3회 중 2회 이상 valid이면 저장소 전체 범위로 고정한다. 아니면 같은 결함으로 범위를 "심은 파일의 최상위 디렉터리"로 좁혀 다시 실행하고, 같은 기준으로 판단한다. 그래도 미달이면 본 실험을 보류하고 설계를 다시 검토한다.
- 파일럿 결과로 바꿀 수 있는 것은 범위 문구, 상한, 반복 수, harness 결함뿐이다. 질문·순위 방향·arm 구성·가설은 바꾸지 않는다.

## 한계 (사전 인지)

- 심은 결함은 검사 하나의 누락이다. 실제 결함보다 단순하다.
- kill 필터 때문에 패키지 단위 테스트가 있는 검사만 뽑힌다. route middleware처럼 통합 테스트로만 검증되는 결함은 과소대표된다.
- 원본 코드는 학습 기준일 이전부터 대부분 존재했다. 모델이 "검사가 있어야 할 자리"를 기억할 수 있다. 이 효과는 세 arm에 같게 작용하므로 비교는 유효하지만, 절대 난이도는 실제 결함보다 낮을 수 있다.
- 저장소가 7개라 크기 조절 효과는 추정만 한다.
