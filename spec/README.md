# Sift 스펙

2026-09-29 초판. 구축된 분석기가 **보장해야 할 것**과 **대상에 맞게 골라야 할 것**을 적는다. 구현 언어와 도구는 정하지 않는다. 구조와 이유는 [설계](../DESIGN.md)에, 결정의 근거는 [ADR](../docs/adr/)에 있다. 참조 구현은 [`boilerplate/`](../boilerplate/)이며 스펙의 일부가 아니다.

- **반드시:** 어기면 결과가 조용히 틀리거나 비용이 새는 요구사항만 둔다. 어떤 대상, 어떤 구성이든 지키며, 어기면 적합성 시험에 실패한다. 식별자(예: `EXT-3`)로 부른다.
- **파라미터:** 에이전트와 사용자가 대상에 맞게 고르는 값. 식별자(예: `P-SELECT`)로 부른다. 스펙은 무엇을 정해야 하고 무엇을 보고 고르며 어디에 기록하는지만 정한다. 고른 값과 이유는 실행 기록에 남기고, [벤치](../bench/)로 대상에서 확인한다. "우리가 쓴 값"은 Sift를 만들며 실험한 예시이지 기본값이 아니다.
- **미정:** 아직 정하지 않은 것.
- **참고:** 참조 구현이 하는 것 중 요구사항은 아닌 것. 다른 언어나 도구로 구현할 때 비용 대비 효과를 따져 고른다.

스펙은 구축된 분석기의 경계, 즉 무엇을 보장하고 무엇을 밖으로 내놓는지만 정한다. 어떻게 구현할지, 대상 범위와 예산처럼 무엇을 합의할지는 정하지 않는다. 대상 범위, Jev 예산, 연구 대상 플랫폼처럼 결과를 크게 바꾸는 선택은 구축할 때 사용자와 합의하고, 합의한 내용을 실행 기록에 남긴다.

## 1. 용어

- **분석 유닛:** 본문이 있는 함수 정의 하나. 같은 원문 범위는 구성이 달라도 한 유닛이다.
- **구성:** 한 번의 파싱이 보는 코드의 모습. C/C++에서는 컴파일 명령, 타깃, 매크로 정의의 조합이다.
- **대상:** 분석할 디렉터리(루트). 루트 밖의 정의는 유닛이 아니다.
- **출발점:** 1차에서 선별된 유닛.
- **묶음:** 출발점과 규칙으로 고른 관련 유닛들. 2차에서 Jev가 묶음 전체를 평가한다.
- **실행 디렉터리:** 한 대상의 한 번의 스캔이 남기는 모든 기록. 같은 디렉터리로 다시 실행하면 이어서 진행한다.

## 2. 함수 추출

- **EXT-1** 루트 안의 소스에서, 도달한 어떤 구성에서든 보인 정의를 모두 유닛으로 낸다. 언어의 모든 정의 형태를 포함한다. C++이라면 클래스 안 정의, friend 함수, 템플릿과 그 부분 특수화, 네임스페이스와 `extern "C"` 안의 정의다.
- **EXT-2** 유닛의 코드는 원문의 해당 범위를 그대로 옮긴 것이다.
- **EXT-3** 같은 유닛을 두 번 평가하지 않는다. 구성마다 시작 위치가 달라지거나 같은 원문이 여러 이름으로 정의돼도 한 유닛이다.
- **EXT-4** 원문에 본문이 없는 정의(본문이 매크로에서 만들어진 경우 등)는 평가하지 않고 보고한다.
- **EXT-5** 전처리기가 있는 언어에서는 함수 경계를 전처리를 거친 파서로 정한다. 관대한 파서는 경계 추정과 보고에만 쓴다.
- **EXT-6** 헤더를 못 찾거나 한 구성의 파싱이 실패해도 스캔을 멈추지 않는다. 실패 횟수를 기록한다.

참고 (참조 구현): 유닛을 파일과 정의의 끝 위치로 식별하고 가장 이른 시작을 쓴다(앞쪽 속성 매크로가 구성마다 시작을 바꾼다). 같은 원문의 여러 이름을 모두 남긴다. 유닛마다 본 구성을 기록한다. 심볼릭 링크 파일은 건너뛴다. 시스템 헤더 경로를 컴파일러 드라이버에서 가져온다.

**P-CONFIGS 구성 탐색 범위.** 어떤 구성까지 파싱할지. 넓힐수록 더 많은 유닛을 보지만 파싱 시간이 는다. 좁히면 COV-1로 보고할 못 본 코드가 늘어난다. 연구 대상 플랫폼이 정해져 있으면 그 구성에 집중할 수 있다.
- *우리가 쓴 값 (C/C++, libclang):* compile DB의 명령. 명령이 없는 루트 안 소스에는 같은 언어 명령 중 가장 흔한 것(없으면 다른 언어 명령에서 언어·표준 플래그를 뺀 것). 각각에 타깃 4개(x86-64·ARM64·i686 리눅스, x86-64 Windows). 추정 도구가 비활성 줄에서 정의를 찾은 곳마다 감싼 `#if` 매크로를 하나씩 켜고 끄고, 둘 이상이면 함께 켜기를 2회까지. 루트 안 소스를 가리키는 명령이 없으면(헤더 전용 라이브러리) 대상 밖 하네스 명령을 쓴다. 7-Zip `C/`에서 compile DB 구성만 쓸 때보다 함수를 약 17% 더 봤고 10코어에서 약 20초 걸렸다([ADR 0014](../docs/adr/0014-python-asyncio-and-code-lookup.md)).

## 3. 범위 기록

- **COV-1** 평가하지 못한 것을 알 수 있는 만큼 보고한다. 적어도 어떤 구성도 파싱하지 않은 파일과, 알고 있지만 평가하지 않은 정의를 보고한다. 구현이 보고할 수 없는 것(예: 구성 밖 코드의 줄 단위 위치)은 무엇인지 실행 기록에 적는다.
- **COV-2** 결과 분류는 확인된 버그, 근거 있는 후보, 기각, 배부됐으나 판정 없음, 미평가·못 봄이다([설계](../DESIGN.md) 3절). 앞의 셋은 에이전트의 판정 기록에서 온다.
- **COV-3 (미정)** 판정 기록의 형식과 명령. 추가 전용이어야 하며, 사람과 에이전트가 함께 쓸 수 있어야 한다.

참고 (참조 구현): 루트 안 모든 줄이 컴파일됐거나, 평가 유닛 안에 있거나, "모든 구성에서 비활성"으로 보고됐거나, 지시문·빈 줄뿐이거나, 파싱하지 않은 파일에 있도록 줄 단위로 회계한다. 평가 유닛 안의 비활성 줄과 지시문만 있는 영역은 보고하지 않는다. 관대한 파서가 비활성 영역에서 찾은 정의의 이름을 함께 보고한다.

## 4. 관계

- **REL-1** 유닛 안의 호출마다 호출 줄과 대상을 기록하고, 대상이 루트 안 유닛(`direct`)인지, 루트 밖(`external`)인지, 정적으로 알 수 없는지(`indirect`, 예: 함수 포인터) 구분한다.
- **REL-2 (미정)** 구조체 필드 읽기·쓰기 관계.

참고 (참조 구현): 대상이 구성마다 다르게 정의되면 모든 정의로 연결한다. 이름은 원문에 적힌 그대로 남긴다(헤더가 `memcpy`를 `__builtin___memcpy_chk`로 바꾼다). `indirect` 호출은 포인터의 필드나 변수 이름을 남긴다. 호출이 호출하는 유닛의 매개변수를 인자로 쓰는지 기록하지만, 이를 이용한 묶음 규칙은 효과가 없었다.

## 5. 1차 전수 선별

- **TRI-1** 모든 유닛을 평가한다. `state`는 유닛의 코드 원문이다. 다른 것을 붙인다면 P-TRIAGE-INPUT으로 정하고 기록한다.
- **TRI-2** 선별은 점수에 대한 결정적 규칙이다. 같은 점수에 같은 규칙을 적용하면 같은 결과가 나온다. 동점은 유닛 식별자로 정한다.
- **TRI-3** 선별 규칙을 정할 때의 모델과 응답 모델이 다르면 그 유닛을 선별하지 않고 오류로 기록한다. 점수 분포는 모델마다 다르다.
- **TRI-4** 모델, 질문과 그 해시, 선별 규칙과 파라미터를 실행 기록에 남긴다.

**P-TRIAGE-QUESTION 1차 모델과 질문.** 대상의 버그 유형과 도메인에 맞게 [질문 라이브러리](../questions/)에서 고르거나 새로 쓴다. 문구가 결과를 크게 바꾸므로 바꾸면 벤치로 다시 확인한다.
- *우리가 쓴 값:* `jev-1.13.0`, `{"type": "noul", "instructions": "Is this function worth a security researcher's time to inspect further for bugs?"}`. Python 6개 사례에서 상위 10% 예산으로 6개 기전 중 5개에 도달했고, 더 복잡한 대조 판단 질문(3/6)과 함수 길이 기준(4/6)보다 나았다([ADR 0004](../docs/adr/0004-first-pass-function-triage.md)).

**P-TRIAGE-INPUT 1차 입력.** 함수 원문 외에 무엇을 붙일지.
- *우리가 쓴 값:* 원문만. 클래스·모듈 선언을 붙여도 도달이 같고 입력 토큰이 약 33% 늘었다.

**P-SELECT 선별 규칙.** 점수로 출발점을 고르는 규칙과 그 값. 출발점 수는 2차 비용과 에이전트가 볼 양을 정한다. 점수 분포는 대상마다 다르다.
- *우리가 쓴 값:* 하한 0.60이면서 대상 안 점수 상위 15%(전체 유닛 수 기준, 올림). 하한만 쓰면 선별량이 대상마다 13.7%~62.5%로 흔들렸다. 1차 실험의 6개 사례 모두에서 결함에 닿는 함수가 상위 15% 안에 들었고, 이를 정할 때 쓰지 않은 4개 사례에서는 결함 지점 3개가 들어가고 libtiff(24.5%)가 빠졌다. 절대 하한 0.80은 urllib3를 놓쳐 기각했다.

## 6. 2차 묶음 재선별

- **BND-1** 출발점마다 묶음 하나를 만들고 묶음 전체에 점수를 준다([ADR 0007](../docs/adr/0007-second-pass-scores-related-code-group.md)).
- **BND-2** 함수 본문을 자르지 않는다. 한도 때문에 넣지 못한 관련 유닛과 `indirect` 호출은 시작 패킷에 "넣지 못한 관계"로 적는다.
- **BND-3** 출력은 에이전트가 볼 순서와 출발점마다의 시작 패킷(묶음의 유닛, 넣지 못한 관계, 미해결 호출)이다.
- **BND-4** 묶음 규칙과 파라미터, 2차 질문을 실행 기록에 남긴다.
- **BND-5 (미정)** 2차 질문과 점수를 합치는 방법, 1차 순위만 쓰는 기준선과의 비교 방법.

**P-BUNDLE 묶음 규칙.** 출발점에서 어떤 관계를 따라 무엇을 넣을지, 한도에 걸리면 무엇부터 뺄지. 좋은 규칙은 대상의 버그 모양에 달려 있다. 벤치의 도달률(버그의 필수 줄이 묶음 안에 있는가)로 고른다.
- *우리가 쓴 후보:* A(출발 함수 + 피호출자), B(A + 호출자), D(B + 호출자의 피호출자), E(A + 피호출자의 피호출자). 가까운 관계부터 넣었다. 설계용 라벨 5개에서 A는 3개, D와 E는 4개 사례에서 필수 줄을 모두 담았고, B는 A보다 커지기만 했다. 한 사례(stb)는 어떤 후보로도 다 담지 못했다([ADR 0016](../docs/adr/0016-second-pass-bundle-principles.md), [실험 요약](../experiments/README.md)).

**P-BUNDLE-BUDGET 묶음 크기 한도.** 모델의 입력 한도와 대상 코드의 글자당 토큰 비율로 정한다. 비율은 대상마다 다르므로 1차 사용량으로 잰다.
- *우리가 쓴 값:* `jev-1.13.0`의 `state`와 질문 합계 32k토큰. 비율은 Expat에서 약 1.84글자/토큰, libtiff에서 약 3.99글자/토큰이었다.

**P-BUNDLE-QUESTION 2차 질문 (미정).**
- *우리가 시험한 것:* 7-Zip 4×5 비교에서 P4(상태 전이), P2(함수 사이 계약), P3(검사와 사용)의 순으로 필수 코드를 담은 후보를 앞에 뒀다. 사례 하나의 부분 결과다.

## 7. Jev 호출

API의 요청·응답 형식, 오류, 한도는 Jev의 공개 문서(https://docs.typesafe.ai)를 따른다.

- **JEV-1** 결과를 (모델, `state`, 질문)으로 캐시하고, 같은 실행 디렉터리로 다시 실행하면 캐시된 요청은 보내지 않는다. 중단된 뒤에도 재개된다. 오류는 캐시하지 않는다.
- **JEV-2** 요청 수 상한에 닿으면 이후 요청은 보내지 않고 "미전송"으로 기록하며, 실행은 멈췄음을 알리는 상태로 끝난다.
- **JEV-3** 계정 오류(HTTP 401·402·403)를 받으면 이후 요청을 모두 보내지 않는다.
- **JEV-4** 입력 한도 초과는 오류와 구분해 "미평가"로 기록한다.
- **JEV-5** API 키를 출력하거나 실행 디렉터리에 쓰지 않는다.
- **JEV-6** 스캔 전에 요청 수와 입력 토큰을 추정해 보여줄 수 있어야 한다.

참고 (참조 구현): 캐시 파일은 추가 전용이며, 마지막 줄이 쓰다 잘려도 무시하고 다음 결과를 새 줄에서 시작한다. 같은 키의 요청이 동시에 나오면 한 번만 보낸다. 일시 오류(408·429·5xx, 연결 오류)는 재시도하고, 점수가 0~1 밖이거나 형식이 틀린 응답은 오류로 기록한다.

**P-JEV-LIMITS 요청 제한.** 동시 요청 수, 요청 수 상한, 재시도 횟수와 간격. 계정의 속도 제한과 크레딧에 맞춘다.
- *우리가 쓴 값:* 동시 16, 재시도 5회(1초부터 두 배씩, 최대 8초). 한 요청에 질문을 하나씩 보내던 4×5 비교가 크레딧을 소진했으므로, 같은 `state`에 질문이 여럿이면 한 요청에 넣는 것이 낫다.

## 8. 실행 디렉터리 형식

JSON Lines 파일은 한 줄에 한 JSON 객체다.

| 파일 | 한 줄(객체)의 필드 |
|---|---|
| `manifest.json` | `target`, `revision`, `started`, `model`, `questions_sha256`, `selection`(규칙 이름과 파라미터), `configs`(구성 이름 목록), `coverage_limits`(구현이 보고할 수 없는 못 본 코드의 종류, COV-1), `summary` |
| `functions.jsonl` | `id`(`경로:시작 줄:이름`), `name`, `path`, `start_line`, `end_line`, `configs` |
| `unanalyzed.jsonl` | `path`, `start_line`, `end_line`, `name`(없으면 null), `reason` |
| `calls.jsonl` | `caller`, `line`, `kind`, `callee`(direct가 아니면 null), `callee_name`, `passes_values` |
| `triage.jsonl` | `function_id`, `status`(scored·unscored·error·unsent), `score`, `detail`, `input_tokens`, `selected` |
| `selected.jsonl` | `triage.jsonl`과 같은 필드, 선별된 것만 순위순 |
| `jev-cache.jsonl` | `key`, `result`(`status`, `scores`, `model`, `detail`, `usage`) |

`summary`는 `functions`, `unanalyzed`(이유별 개수), `parses`, `failed_parses`, `error_diagnostics`, `scored`, `unscored`, `error`, `unsent`, `selected`, `input_tokens`, `stopped`다. `reason`은 자유 문자열이다. 참조 구현은 "inactive in every configuration", "no configuration parsed this file", "body produced by a macro"를 쓰고, 합의한 범위 밖의 코드도 이유와 함께 여기에 적을 수 있다. 2차 출력과 판정 기록의 형식은 미정이다(BND-5, COV-3).

## 9. 적합성 시험
