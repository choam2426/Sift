# 7-Zip 4×5 점수 수집의 부분 평가

2026-09-27 기준. 7-Zip 26.01의 1차 통과 함수 376개 전체를 공통 출발점으로 사용했다. 네 입력 방식이 독립 후보를 만들고, 각 후보에 고정한 P1~P5 질문을 Jev 1.13.0으로 한 번씩 적용했다. 소스 리비전은 `8c63d71ff886bda90c86db28466287f977374237`이다. 요청·응답과 상태 파일은 Git에서 무시되는 `runs/matrix-7zip-26.01-prepared-v6/`에 있다. 아래 수치는 `run-status.json`, `partial-summary-v1.json`, `label-audit.json`에서 계산했다.

## 확보한 응답

| 전체 계획 22,885건 | 건수 |
|---|---:|
| Noul 점수 확보 | 18,882 |
| 입력 한도 초과로 미평가 | 220 |
| HTTP 402로 실패 | 1,385 |
| 전송 전 중단 | 2,398 |

HTTP 402가 연속 발생해 호출을 중단했다. 전체 요청의 82.5%에서 점수를 확보했다. 한 방식·질문당 채점된 후보는 호출 597/746개, 값 1,471/1,779개, 상태 191/224개, 효과 1,517~1,518/1,828개다. 이 수는 채점 가능 범위이며 전체 조건의 완료나 취약점 검증을 뜻하지 않는다. 모든 순위는 **점수를 받은 후보 안에서만** 계산한다.

### 사용량과 호출 방식

성공 응답에서 보고된 입력은 **110,734,835토큰**이었다. 호출 방식 17,199,535, 값 방식 38,509,730, 상태 방식 5,035,875, 효과 방식 49,989,695토큰이다. 질문별로는 각각 약 2,200만 토큰을 사용했다. 한 후보의 같은 `state`를 P1~P5에 **별도 요청 다섯 번** 보낸 것이 주요 원인이다. [TypeSafe의 2026-09-27 모델 문서](https://docs.typesafe.ai/models)의 단가 $0.042/백만 입력 토큰으로 성공 응답분만 단순 환산하면 약 **$4.65**다. 실제 청구액·계정 크레딧·실패 요청의 과금 여부는 이 기록으로 확인할 수 없다. 한정된 크레딧에서 이 실험 한 번이 잔액을 소진했다는 운영상 제약을 작은 단가만으로 무시해서는 안 된다.

[TypeSafe 팬아웃 문서](https://docs.typesafe.ai/patterns/fan-out)에 따르면 한 요청에 여러 질문을 넣고 `state`를 한 번만 처리할 수 있다. 후속 P2·P3·P4 실행에서 세 질문을 한 요청으로 묶는 방법은 **검토할 비용 절감안**이다. 현재 분리 요청의 결과와 동일한 점수가 나온다고 측정한 것은 아니므로, 기존 결과와 섞지 않고 별도 입력·실행 버전으로 확인해야 한다. 함수 본문을 자르거나 후보를 크기로 제외하는 방식은 이 절감안에 포함하지 않는다.

## 알려진 한 사례의 코드 포함 후보 순위

숨긴 [CVE-2026-14266 라벨](../../labels/cve-2026-14266.json)의 필수 소스 줄을 한 후보에 모두 담은 입력은 호출 방식 7개와 상태 방식 1개였다. 값·효과 방식에는 그런 후보가 없었다. 호출 방식의 7개 중 6개는 다섯 질문 모두 채점됐고 1개는 모두 입력 한도 초과였다. 상태 방식의 1개는 다섯 질문 모두 채점됐다. **후보에 필수 코드가 포함됐다는 사실은 Jev가 취약점을 발견했다는 뜻이 아니다.**

| 질문 | 호출 방식: 가장 앞선 필수 코드 포함 후보 | 상태 방식: 필수 코드 포함 후보 |
|---|---:|---:|
| P1 안전 조건 | 119위 / 597개 · 0.53 | 51위 / 191개 · 0.53 |
| P2 함수 계약 | 14위 / 597개 · 0.28 | 26위 / 191개 · 0.27 |
| P3 검사와 사용 | 22위 / 597개 · 0.75 | 33위 / 191개 · 0.72 |
| P4 상태 전이 | **7위 / 597개 · 0.61** | **16위 / 191개 · 0.58** |
| P5 실패 기전 | 139위 / 597개 · 0.36 | 62위 / 191개 · 0.36 |

이 사례에서 P4는 코드가 갖춰진 후보를 두 방식 모두 가장 앞에 놓았다. P2가 그다음이며 P3, P1, P5 순이다. 호출 방식은 가능한 필수 코드 포함 후보가 6개 채점되어 있고 상태 방식은 1개뿐이므로, 두 순위의 숫자만으로 방식의 우열을 비교할 수 없다. 값·효과 방식은 채점 전에 이미 필수 맥락을 한 후보에 모으지 못했다. 이는 Jev 점수보다 후보 생성 범위의 문제다.

2026-09-27 후속 검토에서는 **P2·P3·P4를 우선 질문으로 추리는 방향**을 택했다. 이 선택은 위 한 사례의 부분 순위에 근거한 탐색적 축소이며 질문의 일반 성능이 입증됐다는 뜻은 아니다. P1·P5 점수와 기존 4×5 요청·응답은 비교 기록으로 보존한다. P2는 호출 경계, P3는 선행 검사, P4는 같은 객체의 상태 전이에 근거가 없는 결함을 놓칠 수 있으므로 별도 사례에서 누락을 확인해야 한다.

질문별 Noul 중앙값은 P1 0.43, P2 0.16, P3 0.64, P4 0.41, P5 0.27이었다. 질문마다 점수 기준선이 크게 다르므로 절대 점수나 공통 임계값으로 질문의 성능을 비교하지 않는다. 위 표는 각 질문 **안에서의 순위**를 보여준다.

## 해석 범위

이 평가는 HTTP 402 이후 점수가 없는 요청을 제외한 부분 결과이며 한 번의 Jev 응답만 사용한다. 아직 점수가 없는 후보가 나중에 높은 점수를 받으면 표의 순위는 뒤로 밀릴 수 있다. 알려진 7-Zip 라벨은 입력 감사와 기존 파일럿에서 이미 참조됐으므로 독립 검증 사례가 아니다. 3차 에이전트의 코드 조사나 오류 기전 확인도 아직 수행하지 않았다. 따라서 P4가 이 사례에서 유망하다는 신호는 있으나 네 입력 방식·다섯 질문의 일반적인 취약점 검출 성능이나 최종 우열은 판단할 수 없다.
