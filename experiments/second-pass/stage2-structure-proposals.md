# 2차 구조 후보 다섯 가지 (제안)

상태: 2026-10-08 제안. **같은 날 2번(싱크 역방향 슬라이스)을 첫 구현 대상으로 채택했다([ADR 0027](../../docs/adr/0027-sink-slices-with-own-dataflow-library.md)).** 나머지 후보는 미결로 남는다. 기존 묶음 방식(A·B·D·E)과 [ADR 0026](../../docs/adr/0026-prioritize-callsite-candidates-and-adaptive-expansion.md)의 호출지점 경계(P·R·C)를 일단 배제하고, 효과적인 2차 구조를 처음부터 다시 생각한 후보다. 채택하면 ADR로 옮기고 이 문서는 근거로 남긴다.

## 출발점이 되는 사실

[설계 6절](../../DESIGN.md#6-근거와-한계)과 [실험 요약](../README.md)에서 확인된 것.

- 1차 Noul 점수는 함수 길이와 강하게 상관한다(Magma 3개 대상에서 로그 길이와 0.71~0.80). 묶음 점수도 묶음 크기와 상관했다.
- 판정 대상을 표시하고 호출 관계 문맥을 붙여도 AUC는 같았고, 점수는 버그 여부와 무관하게 약 0.02씩 일정하게 내려갔다. **절대 점수로 관계를 읽는 시도는 구조적으로 불리하다.**
- 수정 전후 버전의 점수가 거의 같다. Jev는 "버그가 있다"보다 "버그가 있을 법한 코드 모양"을 본다.
- Jev는 요청 하나에 Noul·Choice 질문을 여러 개 실을 수 있고, 같은 상태는 캐시된다(`sift.jev`).
- CyberGym `arvo:10400`에서 1차 단독은 파서 `ReadMNGImage`(63위)는 잡고 실제 결함 헬퍼 `mng_get_long`(9,610위)은 놓쳤다. 둘 사이에 직접 호출 24곳이 있다([ADR 0025](../../docs/adr/0025-restore-second-jev-stage.md)).

## 후보

### 1. 역할 태깅 → 결정적 source→sink 사슬

1차 요청에 Choice 질문을 더 실어 함수마다 역할 확률을 받는다. 예: 외부 입력을 파싱하는가, 입력에서 크기·오프셋을 계산하는가, 원시 메모리 접근을 하는가, 검증만 하는가. 2차는 Jev 없이 호출 그래프에서 **파서 → 크기 계산 → 메모리 접근** 사슬을 찾고, 중간에 검증 역할이 없는 사슬을 역할 확률의 곱으로 순위화한다.

- 근거: Jev를 탐지기가 아니라 분류기로 쓴다. 분류는 길이 편향에서 비교적 자유롭고, 수정 전후 점수가 같다는 사실도 역할 분류에는 문제가 아니다. `ReadMNGImage → mng_get_long`이 정확히 이 사슬이다.
- 비용: 1차 재실행 한 번. 2차 요청 0.
- 가장 싼 검증: Magma 라벨 3개 대상에 역할 질문을 붙여 재실행하고 버그 함수를 포함한 사슬의 순위를 본다.
- 리스크: 역할 질문의 분류 품질을 모른다. 라벨 몇십 개로 먼저 확인한다.

### 2. 싱크 기준 역방향 슬라이스

원자를 호출지점이 아니라 **위험 연산**(배열 인덱싱, 포인터 산술, `memcpy` 류, 할당 크기 계산, 정수 형변환)으로 둔다. 싱크마다 토큰 한도 안에서 값의 출처까지 거슬러 올라간 슬라이스를 후보 하나로 만들어 Jev에 보낸다.

- 근거: CyberGym 오라클은 sanitizer 충돌이고 충돌 지점은 싱크다. 후보 단위와 평가 단위가 일치한다. 싱크 수는 유한해 후보 폭발이 없다. 슬라이스는 함수에서 무관한 코드를 **빼므로** 지금까지의 반대 신호(코드를 더 붙이면 나빠진다)와 방향이 반대다. `mng_get_long`의 4바이트 읽기에서 거슬러 오르면 `ReadMNGImage`의 청크 길이 검사 유무가 한 슬라이스에 들어온다.
- 비용: 싱크 수만큼 요청. 슬라이스는 함수보다 작은 경우가 많다.
- 가장 싼 검증: `arvo:10400`에서 `mng_get_long` 싱크 슬라이스가 길이 검사까지 닿는지와 그 순위.
- 리스크: 슬라이서 구축 비용. 아래 "슬라이서 선택" 참조.

### 3. 쌍대 비교 토너먼트

후보 둘을 한 상태에 넣고 Choice로 어느 쪽에 결함이 있을 가능성이 높은지 묻는다. 스위스식이나 Elo로 약 n log n 번 비교해 순위를 만든다.

- 근거: 추정 대상을 절대 점수에서 상대 선호로 바꾼다. 문맥에 따른 일정한 하락이 상쇄되고, 두 후보를 같이 보여주므로 길이 편향이 줄 여지가 있다. Jev를 비교기로 쓴 적은 없다.
- 비용: 1차 통과 3,400개 기준 약 4만 비교. 상태당 토큰은 두 함수 합.
- 가장 싼 검증: Magma 라벨과 캐시된 함수 본문으로 바로 가능. 수천 요청으로 AUC와 코드 30% 예산 도달 수를 1차 순위와 비교한다.
- 리스크: 위치 편향과 비교 질문을 Jev가 학습하지 않았을 가능성. 위치를 뒤집어 두 번 물으면 둘 다 진단된다.

### 4. 문맥 델타 점수

같은 대상 함수를 단독으로, 그리고 특정 caller의 호출지점 문맥을 붙여서 두 번 채점하고 점수 **차이**로 caller-callee 쌍을 순위화한다. 절대 점수는 버린다.

- 근거: 문맥이 AUC를 안 바꾼다는 결과는 절대 점수 얘기였고 델타는 측정한 적이 없다. 일정한 하락분은 상수로 빠진다. `mng_get_long` 단독은 낮지만 `ReadMNGImage`의 길이 미검사 호출 문맥에서 오르는지가 보고 싶은 것이다.
- 비용: 쌍 수만큼 요청. 피호출자 하나에 caller가 많으면 비싸다.
- 가장 싼 검증: 기존 "TARGET 표시 + 문맥" 실험 캐시와 단독 점수를 짝지어 델타를 계산하면 요청 없이 첫 답이 나온다.
- 리스크: 델타가 잡음 수준일 수 있다. 같은 상태를 두 번 보내도 결과가 같은지(결정성)부터 확인한다.

### 5. 입구 도달 경로 순위

퍼징 하네스나 공개 API 같은 입구에서 **도달 가능한 호출 경로**를 후보로 삼고, 경로상 노드의 1차 점수와 "인자가 입력에서 유도됨" 간선 속성으로 경로를 순위화한다. 도달 불가능한 함수는 평가에서 뺀다.

- 근거: 하네스에서 닿지 않는 코드는 충돌할 수 없다. 도달 가능 집합이 전체의 일부라면 다른 모든 안의 비용을 줄인다. 경로 단위면 낮은 피호출자가 높은 caller의 경로 안으로 들어온다.
- 비용: Jev 추가 요청 0. 호출 그래프와 간접 호출 처리만 필요하다.
- 가장 싼 검증: `arvo:10400`의 도달 가능 집합 크기와 `mng_get_long` 포함 여부.
- 리스크: Magma에서 호출 그래프 규칙으로 1차를 보강했을 때 유닛 예산 기준으로 더 못 닿았다. 그때는 도달성 필터가 아니라 점수 보정이었고 예산도 코드 양이 아니었다. 간접 호출이 많은 대상에서는 도달 집합이 틀릴 수 있다.

## 판단 (제안자 의견)

- **가장 유망한 것은 2번.** 후보 단위가 오라클과 일치하고, Jev에 보내는 코드를 늘리는 대신 줄이며, 놓친 사례를 정확히 설명한다. 약점은 슬라이서 구축 비용 하나다.
- **먼저 돌릴 것은 3번과 4번.** 기존 캐시와 Magma 라벨로 요청 몇천 건 이내에 답이 나온다. 3번 결과가 좋으면 2번 슬라이스의 순위화에 절대 점수 대신 비교를 쓸 수 있어 두 안이 합쳐진다.
- **5번은 Jev 비용이 없고 나머지의 전제**라 병행한다. 1번은 1차 재실행이 필요하지만 2차 비용이 없어 그다음이다.

## 슬라이서 선택 (2번의 전제)

- **CodeQL은 쓰지 않는다.** MIT인 것은 질의·라이브러리뿐이고 C/C++ 추출기와 엔진은 비공개 CLI다. 약관상 비공개 코드와 자동 분석에 유료 라이선스가 필요하다([ADR 0014](../../docs/adr/0014-python-asyncio-and-code-lookup.md)). 공개 벤치 실험만이면 가능하지만, CodeQL 없이 재현되지 않는 방법은 비공개 대상에 쓸 Sift의 근거가 되지 못한다.
- **Joern(Apache 2.0)은 학술적으로 검증됐으나 정밀도는 CodeQL급이 아니다.** Code Property Graph 원 논문(Yamaguchi 외, IEEE S&P 2014)의 구현체이고 취약점 탐지 연구의 그래프 추출에 가장 널리 쓰인다. 그러나 C/C++에서 기본으로 전처리를 하지 않고, alias·포인터 분석이 없으며 간접 호출을 풀지 않는다. ADR 0014에서 7-Zip의 `#include`된 `.c` 35개 누락과 1000자 절단을 오류 없이 지나치는 **조용한 누락**을 확인했다. 연구 커뮤니티가 쓰는 이유는 정밀해서가 아니라 오픈소스이고 빌드 없이 돌기 때문이다.
- **libclang 위에 얕은 절차간 슬라이서를 직접 만드는 쪽을 제안한다.** 우리 용도에 한해 Joern보다 나을 수 있다. 이기는 축은 입력 충실도다. 이미 compile DB와 실제 헤더로 모든 `#if` 구성을 파싱해 함수와 호출지점을 정확히 갖고 있고, 슬라이스의 가장 치명적인 실패는 코드를 못 본 것이다. 지는 축은 흐름 분석의 깊이다. alias, 포인터 필드, 간접 호출은 풀지 못하고 함수 내 도달 정의 + 인자↔매개변수 + 반환값까지가 현실적이다. libclang은 CFG를 주지 않으므로 AST에서 직접 만들어야 하며(C의 `goto` 오류 처리 포함) 1~2주 작업으로 본다.
- 이것이 괜찮은 이유: 슬라이스는 증명이 아니라 Jev 입력이다. 토큰 한도 안의 과대 포함은 허용되고, 못 푼 관계는 ADR 0026대로 미해결로 기록한다. 정밀한 흐름 분석이 Jev 순위를 개선한다는 근거가 없으므로 깊이에 투자하기 전에 얕은 슬라이스로 효과부터 본다.
- 어떤 슬라이서든 "검증된 도구인가"가 아니라 **"이 대상에서 이 슬라이스가 필수 줄을 담는가"를 라벨로 검사하는 절차**가 먼저 있어야 한다. 과대 포함은 비용이고 과소 포함은 결함을 못 보는 것이다.
