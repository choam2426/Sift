# 2차 분석 A 기준선 실험 설계

> **2026-09-27 실험 상태:** [4×5 비교 설계](design-comparison.md#첫-7-zip-점수-수집--2026-09-27-중단-상태)의 첫 7-Zip 점수 수집은 HTTP 402가 연속 발생해 중단했다. 22,885건 중 18,882건 채점, 220건 입력 한도 초과, 1,385건 HTTP 402, 2,398건 미전송이다. [확보한 점수의 부분 평가](partial-results-7zip-2026-09-27.md)는 별도로 기록했으며 전체 조건의 비교 결과는 아직 없다.

> **2026-09-27 재설계:** [ADR 0009](../../docs/adr/0009-compare-four-second-pass-inputs.md)에 따라 호출 흐름·값의 흐름·상태 변화·효과 중심의 네 가지 입력 구성을 모두 비교한다. [비교 설계와 프롬프트 후보](design-comparison.md)에 합의 범위와 미합의 제안을 구분했다. 아래의 기존 실행 조건과 국소 파일럿은 기록으로 보존하며 새 비교 실험의 확정된 입력·프롬프트로 간주하지 않는다.

> 상태: 2026-09-25 설계 재검토 중. **A를 먼저 실행**하는 순서는 [ADR 0005](../../docs/adr/0005-second-pass-a-baseline.md), **CodeQL DB는 코드 사실을 제공하고 Jev가 취약성을 판단**하는 역할은 [ADR 0008](../../docs/adr/0008-codeql-db-facts-jev-vulnerability-judgment.md)에 기록했다. 직접 호출 1홉으로 후보를 만들던 입력은 CodeQL 데이터베이스의 의미 관계를 충분히 쓰지 못한다는 지적에 따라 **실행을 보류**했다. [CodeQL 데이터베이스 기반 대안](codeql-evidence-proposal.md)을 검토한 뒤 후보 경계와 입출력을 다시 확정한다. 기존 묶음 평가 단위·중복 규칙은 [ADR 0007](../../docs/adr/0007-second-pass-scores-related-code-group.md)에 기록되어 있다.

아래 직접 호출 1홉 규칙과 367개 후보의 실행 단계는 **이전 설계 기록**이다. 새 입력 계약이 정해지기 전까지 채점 계획으로 실행하지 않는다.

2026-09-25에는 [CodeQL DB 상태 객체 국소 파일럿](codedb-state-pilot.md)으로 **1차 출발 함수 하나에서 5개 동작 후보를 만들고 Jev를 각 1회 호출**했다. 이는 입출력과 누락을 확인한 탐색 실험이며 전체 A 기준선 채점이 아니다.

2026-09-26에는 [CodeQL 의미 관계 추가 국소 실험](codedb-semantic-probe.md)에서 자료 흐름·조건의 효과·가능한 `Code2` 대입 근거를 추가했다. 넓은 관계 입력은 Jev의 `state`+질문 32k토큰 한도로 거절됐고, 출력 경로에 집중한 `p->decoder` 입력은 채점됐으나 단일 Noul 값이 `0.28`에서 `0.19`로 내려갔다. 이를 A의 일반 성능으로 해석하지 않는다.

같은 날 [단순 입력 재시험](codedb-semantic-probe.md#단순-입력-재시험)은 전체 함수 본문을 유지하고 중복 조건·필드 접근 목록을 Jev 입력에서 제거했다. 다섯 후보의 입력 토큰 합계가 66,690에서 30,768로 줄었고, `p->decoder`의 1회 점수는 `0.28`에서 `0.26`으로 바뀌었다. 이 표현은 **검토할 제안**이며 A 기준선 규칙은 아직 확정하지 않았다.

Sift는 모든 함수를 [1차 기본안](../../docs/adr/0004-first-pass-function-triage.md)으로 평가하고, 통과한 함수를 출발점으로 관련 코드 묶음을 구성해 다시 선별한 뒤 LLM으로 심층 분석한다. 이 실험은 **A: 코드에서 추출한 관계를 규칙으로 묶고 Jev가 묶음 전체를 2차 판단**하는 흐름을 먼저 검증한다. A의 입력과 결과를 고정하면 나중에 다른 관련 코드 선택 방식이나 판단 주체를 같은 조건에서 비교할 수 있다. Jev 점수는 조사 우선순위 신호이며 버그 확률이나 finding의 근거가 아니다.

## 비교 대상과 분석 단위

- **출발 함수:** 1차를 통과한 함수 하나. 이 함수는 2차 후보를 만드는 소스이며, 2차 점수는 새로 만든 관련 코드 묶음 전체에 준다. 동일 묶음은 한 번만 평가하고 겹치지만 구성이 다른 묶음은 별도 후보로 둔다.
- **A 기준선:** 각 출발 함수에서 규칙으로 관련 코드를 고르고, 연결된 코드와 관계 근거를 Jev에 보내 묶음 전체를 평가한다. 현재 검토 중인 질문은 그 묶음에 구체적인 보안 취약점이 있는지다. 묶음 점수순으로 3차 분석 대상을 고른다.
- **내부 참조:** 1차 함수 점수와 순위를 보관한다. 2차 점수는 함수 묶음에 주므로 함수 점수와 절대값이나 순위를 일대일로 비교하지 않는다. 1차 출발 함수에서 알려진 기전과 3차 분석 대상으로 얼마나 도달하는지 비교한다.
- **향후 비교:** B(가벼운 LLM이 관계 후보에서 코드를 선택하고 Jev가 판단), C(가벼운 LLM이 코드 선택과 2차 판단을 모두 수행)는 이번 실행 범위에 넣지 않는다. 나중에 비교한다면 A의 입력 스냅샷, 관계 후보와 3차 예산을 재사용한다.

## 먼저 확정할 2차 입력

2차 실행 전에 [CodeQL 데이터베이스 기반 대안](codeql-evidence-proposal.md)과 [기존 1홉 입출력안](io-v1.md)을 비교해 후보 생성과 요청·응답 계약을 다시 고정한다. **크기로 함수를 제외하지 않는다.** [이전의 앵커 함수 평가 입력](input-v1.md)은 사전 점검 기록이다. 관계의 방향과 원본 근거를 보존하고, 1차 점수·리비전·취약점 라벨은 모델에 보내지 않는다.

### 기존 도구로 관계를 얻을 수 있는 범위 — 2026-09-24 확인

[CodeQL 호출 관계 파일럿](codeql-pilot/README.md)은 2026-09-24에 C, C++, Rust, Go, Python 스냅샷에서 각각 데이터베이스와 질의를 실행했다. 다섯 언어 모두 원본 위치가 있는 일부 호출 관계를 얻었고, 7-Zip의 함수 포인터 및 urllib3의 동적 메서드 호출이 미해결로 남는 것도 확인했다. [ADR 0006](../../docs/adr/0006-codeql-source-relation-experiment.md)은 **A 실험 도구로 CodeQL을 사용**하기로 한 범위를 기록한다. 제품 기본 도구 채택과 입력에 넣을 관계 판정은 별도 검토 대상이다.

[직접 호출 입력 사전 점검](direct-call-dry-run.md)은 2026-09-25에 7-Zip의 1차 통과 함수 376개 전부를 출발점으로 CodeQL 직접 호출 기반의 **이전 `target` 중심 `state`**를 Jev 호출 없이 생성했다. 관계 함수가 붙은 입력은 297개이며, 알려진 버그의 필수 소스 줄은 한 입력에 모두 포함됐다. 79개 입력의 관계 부재와 추출 누락도 함께 기록했다. 이 결과는 관계·코드 도달 점검에 쓰며, 새 묶음 평가 입력이나 2차 점수·버그 검출 결과로 취급하지 않는다.

[크기 제한 없는 묶음 사전 점검](direct-call-group-dry-run.md)은 같은 376개 출발 함수의 직접 호출 이웃을 모두 포함하고 동일한 묶음 9개를 제거해 **367개 후보**를 만들었다. 이 입력은 Jev로 아직 채점하지 않았다. 이전의 크기 기반 사전 점검 결과는 새 후보 수나 버그 맥락 도달을 대신하지 않는다.

첫 A 기준선에는 **원본 호출 위치로 확인한 직접 호출 관계만** 사용한다. CodeQL은 관계 후보와 근거 위치를 제공하며, 묶음 구성·입력 생성과 2차 판단은 별도 단계다. 이 입력으로 2차 순위와 버그 도달·누락 원인을 측정한 후, 간접 호출·필드 흐름은 별도 입력 버전에서 검증한다. 이 범위 결정은 [ADR 0006](../../docs/adr/0006-codeql-source-relation-experiment.md)에 기록했다. JSON 구조·질문과 2차 실행 수치는 아직 검토할 제안이다.

저장소의 [`extract_clang.py`](../first-pass/extract_clang.py)는 현재 함수 정의와 원본 위치만 추출하며 관계 그래프를 만들지는 않는다. 다만 로컬 Clang으로 7-Zip 26.01의 `C/XzDec.c`를 `-std=c99 -fsyntax-only`로 파싱하고 AST를 확인한 결과, **그래프의 근거가 될 자료는 이미 얻을 수 있었다.** `XzUnpacker_Code`의 1071행은 `MixCoder_Code` 직접 호출, 1203행은 `XzDecMix_Init` 직접 호출로 식별됐다. `MixCoder_Code` 610행의 `IStateCoder.Code2`는 함수 포인터 호출로, 292·455행의 구현 함수 대입은 같은 필드 선언에 연결됐다. `CMixCoder.outWritten`은 `MixCoder_Init` 536행과 `MixCoder_Code` 632·642행, `CMixCoder.numCoders`는 `XzDecMix_Init` 931행과 `MixCoder_Code` 637행에서 같은 필드 선언으로 식별됐다. 이 결과는 모델을 호출하지 않은 로컬 AST 점검이다.

**직접 호출 간선은 기존 Clang AST에 작은 변환기를 붙여 만들 수 있다.** 함수 포인터의 대입 목록만으로 호출 시의 실제 대상을 한 개로 확정할 수는 없다. 예를 들어 362행의 다른 `Code2` 대입은 `USE_SUBBLOCK` 조건부 코드라 이번 기본 컴파일 구성의 AST에 나타나지 않았다. 또한 같은 필드 선언을 참조한다는 사실만으로 함수들이 **동일한 객체**를 다룬다고 증명할 수 없다. `&p->decoder`의 전달과 별칭을 추적해야 상태 흐름 간선을 만들 수 있다. 따라서 간접 호출·필드 후보는 증명 가능한 연결만 입력에 넣고 나머지를 `unresolved`로 기록하는 것이 현재 제안이다. 전체 C/C++ 범위에서는 각 파일의 매크로·헤더·빌드 옵션을 맞춘 [컴파일 명령 데이터베이스](https://clang.llvm.org/docs/JSONCompilationDatabase.html)가 필요하다. [Clang LibTooling과 AST Matcher](https://clang.llvm.org/docs/LibASTMatchersTutorial.html)는 이 AST 자료를 독립 도구로 추출하는 공식 경로다. Rust·Go의 기존 tree-sitter 추출기는 구문상 함수 목록을 제공하지만 이와 같은 타입·별칭 해석 그래프를 아직 제공하지 않는다.

## 입력 준비와 누출 방지

1. 대상 리비전과 추출기 버전을 고정하고 함수 ID·본문·위치·원본 해시를 만든다. 1차는 대상 함수 **전체 본문만** 평가하고 성공한 유닛 중 `Noul ≥ 0.60`을 2차 묶음 구성의 출발 함수로 추출한다. 점수 내림차순, 동점이면 유닛 ID 오름차순이다. 모델·질문·입력 표현이 [ADR 0004](../../docs/adr/0004-first-pass-function-triage.md)의 조건과 다르면 `0.60`을 적용하기 전에 확인한다.
2. 7-Zip 취약 버전 26.01은 [코드 본문만 사용하는 입력으로 지정된 55개 C 파일의 함수 602개를 모두 재평가](../first-pass/README.md)했다. 원시 응답과 `Noul ≥ 0.60`으로 고른 **376개**는 Git 제외된 `experiments/first-pass/runs/7zip-26.01-code-only-v1/`에 있다. 수정 버전 26.02의 기존 600개 점수는 `Function:` 헤더가 있는 다른 입력 형식이므로 A에서 짝 비교하기 전에 `code-only-v1`으로 다시 평가해야 한다. 이 파일 범위 밖의 C 파일 18개는 평가하지 않았으며 7-Zip 전체 코드베이스의 완료로 세지 않는다. 기존 `data/7zip.c.memory.scores.jsonl`의 602개 응답은 당시 질문과 입력을 완전히 재구성할 수 없어 사용하지 않는다.
3. 모델 입력에는 취약점 이름·라벨·패치 차이·수정 여부를 넣지 않는다. 각 버전을 별도 대상 스냅샷으로 처리한다. 수정 버전은 대응 동작을 살피는 제한적 비교 자료로 쓰며, 전체를 비버그로 라벨링하지 않는다.
4. 입력 스냅샷은 원본 리비전, 함수 목록과 코드 해시, 1차 질문·모델·원시 응답, 관계 추출기 버전과 후보 목록을 묶어 식별한다. 2차 질문·모델·설정, 실행 순서와 재시도 정책도 실행 전에 고정한다.

## A의 관련 코드 선택 규칙 제안

관계 후보는 정적 코드에서 **근거 위치가 확인되는 것만** 만든다. 직접 호출의 호출자·피호출자, 호출 지점까지 대상 바인딩을 좁힌 함수 포인터 호출, 같은 객체 또는 확인된 별칭의 상태 필드에 대한 쓰기·읽기 관계를 후보로 둔다. 단순히 이름이 비슷하거나 같은 파일에 있다는 이유만으로 연결하지 않는다. 함수 포인터의 대상이 여러 개이거나 필드의 소유 객체·별칭을 연결하지 못하면 `unresolved`로 기록한다. 간접 호출을 통한 도달률은 별도로 보고한다.

첫 버전은 출발 함수에서 **한 관계 단계**로 직접 연결된 모든 함수를 사용하고, 호출 위치·관계 종류·함수 ID를 기록한다. 간접 호출과 필드 관계를 추가하는 버전에서는 바인딩·필드 근거를 따로 정의한다. 같은 함수가 여러 관계로 연결되면 본문은 한 번만 넣고 모든 근거를 보존한다. 포함된 함수들 사이에 확인된 직접 호출 관계도 모두 넣는다. 해석되지 않은 호출과 실제 모델이 거부한 입력은 별도 기록한다.

해결된 간접 호출과 상태 필드 흐름은 첫 기준선에 넣지 않고 별도 입력 버전에서 검토한다. 입력 크기는 생성 후 측정하며, **크기로 관련 함수를 제외하거나 코드를 자르지 않는다.** 실제 API가 입력 한도를 이유로 거부하면 그 묶음을 `oversize` 미평가로 기록한다. 실제 요청 토큰도 기록한다. 이 규칙은 정답 라벨에 맞춰 특정 함수나 필드를 추가하지 않는다. 버그를 설명하는 데 필요한 코드가 빠지면 누락 원인을 관계 부재, 한 단계 제한, 추출 실패로 나눠 보고하고, 바꾼 규칙은 새 버전의 A로 기록한다.

## 2차 판단과 3차 분석 제안

- 2차 질문은 **입력에 포함된 함수와 관계가 구현한 동작에 구체적인 보안 취약점이 있는지** 직접 묻는 안을 검토한다. 일반적인 조사 가치보다 더 좁은 판단이므로, 제시된 코드에서 취약 기전과 보안 영향을 뒷받침할 수 있어야 한다. 1차는 함수의 조사 가치, 2차는 묶음의 취약성 판단 신호이므로 두 점수의 절대값을 직접 비교하지 않고, 동일한 예산의 기전 도달과 입력 누락을 본다. 낮은 점수는 안전성의 증명이 아니다. 원시 응답과 `Noul` 값만 기록하며 모델이 제공하지 않은 이유나 코드 위치를 만들어 넣지 않는다.
- 2차는 동일한 묶음 입력에 **3회 독립 요청**하는 방안을 제안한다. 반복별 순위 변동을 보고하고, 세 응답이 모두 성공하면 `Noul` 중앙값 내림차순·묶음 ID 오름차순으로 최종 순서를 고정한다. 통과 예산과 상위 구간은 중복 처리 후 실제 묶음 수를 확인해 고정한다. 1차의 `0.60`을 근거 없이 2차 임계값으로 재사용하지 않는다. 응답 실패는 낮은 점수로 바꾸지 않고 2차 미평가로 표시한다.
- 작은 종단 확인의 3차 호출 수와 모델·도구·호출당 토큰 상한은 묶음 평가 단위와 중복 처리 규칙을 확정한 뒤 정한다. 향후 방식과 비교할 때 같은 스냅샷에 같은 예산을 적용한다.
- 작은 종단 확인에서는 A의 출력에 동일한 심층 LLM, 동일한 코드 조회 도구와 예산을 적용한다. 3차는 대상 동작, 의심 조건, 관련 방어 검사와 근거 위치, 다음 검증 방법을 남긴다. 재현 가능한 오류 기전과 단순 후보를 [제품 명세](../../docs/product.md)에 따라 구분한다.

## 실행 단계

1. **2차 입출력 확정:** [묶음 평가 입출력 설계](io-v1.md)의 요청·응답 구조, 질문·직렬화와 오류 기록을 고정한다. [크기 제한 없는 사전 점검](direct-call-group-dry-run.md)의 367개 후보와 원본 코드를 대조했으며, 이 단계에서는 모델 호출을 하지 않았다.
2. **관계·작동 확인:** 준비된 7-Zip 26.01의 지정 범위 함수·`code-only-v1` 1차 응답을 사용한다. 26.02의 짝 비교는 같은 입력 형식의 1차 점수를 확보한 뒤 진행한다. [CVE-2026-14266 라벨](labels/cve-2026-14266.json)의 필수 맥락은 모델에 보이지 않는 채점 자료로만 쓴다. 관계 후보의 근거가 원본 코드와 맞는지, 필수 맥락이 선택된 묶음에 들어오는지 확인한다. 이 사례에서 발견한 추출 오류를 고칠 수 있으나 수정마다 A 버전과 실행을 분리한다.
3. **A 2차 실행:** 고정된 1차 통과 함수에서 같은 관계 규칙으로 묶음을 구성하고 묶음 전체를 평가한다. 출발 함수와 묶음의 대응, 선택·누락·Jev 응답과 비용을 모두 남긴다. 묶음 점수순의 기전 도달 곡선을 1차 함수 순서의 도달과 비교한다.
4. **작은 종단 확인:** 미리 정한 3차 예산으로 A의 상위 묶음을 분석한다. 알려진 버그가 근거 있는 finding으로 이어졌는지와 전체 비용·시간을 확인한다. 7-Zip 한 사례로 구조의 일반 성능을 주장하지 않는다.
5. **별도 사례:** 취약 소스와 유사 동작의 검토된 비버그 사례, 디컴파일 코드 사례를 각각 확보해 독립적으로 실행한다. 7-Zip 결과를 보고 규칙과 질문을 조정했다면 별도 사례 결과로 다시 조정하지 않는다. 소스와 디컴파일 결과는 분리한다. 현재 저장소에는 이 단계의 2차 라벨과 디컴파일 입력 스냅샷이 준비돼 있지 않다.

## 기록과 판정

각 실행의 원시 자료는 Git에서 제외한 `experiments/second-pass/runs/<run-id>/`에 둔다. 입력 스냅샷과 A 버전, 묶음 ID와 출발 함수 ID의 대응, 관계 후보와 증거 위치, 선택한 함수와 제외 이유, 실제 입력 해시, 2차 응답, 3차 순서, 모델·질문 버전, 토큰·비용·지연, 오류와 재시도를 기록한다. 라벨은 별도 파일에 둔다.

버그 기전마다 **1차 출발 함수 선발 → 허용된 관계로 도달 가능 → 선택된 2차 묶음에 포함 → 묶음의 2차 예산 통과 → 3차 도달 → 근거 있는 finding**을 구분한다. 여러 묶음이 같은 버그에 도달해도 버그 기전은 한 번만 센다. 관계상 닿지 못한 버그와 닿았지만 묶음 구성 또는 2차 순위 때문에 탈락한 버그를 섞지 않는다. 관련 코드 포함률, 검토된 비버그 통과량, 미검토 함수 수, 전체 비용·시간을 함께 보고한다.

**실행 전 확정할 값:** JSON 구조·질문, 위의 제안 수치, 3차 모델·도구·호출당 토큰 상한, 재시도 정책, 별도 사례와 제한적 비버그 라벨, A 기준선의 채택 판정 기준. 버그 도달과 근거 있는 finding의 보존을 비용 절감보다 우선한다. A의 버전과 이 값들을 고정한 뒤에만 향후 B·C와 직접 비교한다.
