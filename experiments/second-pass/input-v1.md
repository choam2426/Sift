# A의 2차 Jev 입력 형식 이전 제안

> 상태: 2026-09-25 **2차 채점용으로 사용하지 않는 이전 제안**. [ADR 0007](../../docs/adr/0007-second-pass-scores-related-code-group.md)에 따라 2차 점수는 관련 코드 묶음 전체에 주고, 크기를 이유로 함수를 제외하지 않는다. 아래 `target` 중심 구조·질문과 28,000바이트 선택 규칙은 기존 [직접 호출 사전 점검](direct-call-dry-run.md)의 기록으로만 보존한다. 현재 요청·응답은 [묶음 평가 입출력 설계](io-v1.md)에서 다룬다.

## 판단 대상

2차 요청 한 건은 1차를 통과한 **앵커 함수 하나**를 판단한다. 아래 `target`이 앵커이고 `related_functions`는 그 판단에 쓰는 코드 맥락이다. 관련 함수가 자체로 1차를 통과했는지, 알려진 결함을 포함하는지는 입력에서 알리지 않는다. 관련 함수가 여러 관계로 연결되어도 코드는 한 번만 싣는다. 관련 함수를 찾지 못하면 두 배열을 비운 채 앵커만 보낸다.

[TypeSafe의 State 문서](https://docs.typesafe.ai/concepts/state)는 관계가 있는 자료에 이름을 붙인 JSON 객체를 권장한다. 따라서 `state`는 다음 구조의 객체로 제안한다. 예시의 코드 문자열은 설명을 위해 줄였으며 실제 요청에는 해당 함수의 원본 **전체 본문**을 넣는다.

```json
{
  "target": {
    "key": "T",
    "file": "C/XzDec.c",
    "start_line": 580,
    "end_line": 785,
    "symbol": "MixCoder_Code",
    "code": "<C/XzDec.c:580-785의 원본 전체 코드>"
  },
  "related_functions": [
    {
      "key": "R1",
      "file": "C/XzDec.c",
      "start_line": 1015,
      "end_line": 1369,
      "symbol": "XzUnpacker_Code",
      "code": "<C/XzDec.c:1015-1369의 원본 전체 코드>"
    }
  ],
  "relations": [
    {
      "kind": "direct_call",
      "from": "R1",
      "to": "T",
      "evidence": [
        {
          "file": "C/XzDec.c",
          "start_line": 1071,
          "end_line": 1074,
          "code": "<호출 지점의 원본 네 줄>"
        }
      ]
    }
  ]
}
```

`T`·`R1` 등은 **요청 안에서만 쓰는 키**다. 실제 함수 ID와 소스 리비전은 실행 기록에서 이 키에 대응시키며 모델에는 보내지 않는다. 현재 Rust·Go 함수 ID에는 버전 번호가 포함되어 있으므로 이를 그대로 모델에 보내면 취약·수정 태그를 드러낼 수 있다. 파일·줄·심볼은 코드 출처를 찾는 데 필요한 사실로 보낸다. `relations.from`·`to`는 실제 코드의 관계 방향이며 앵커를 항상 출발점으로 둔다는 뜻이 아니다. 첫 A 기준선의 관계 종류는 원본 호출 위치로 확인한 `direct_call`이다. 이후 확장한다면 호출 지점까지 대상 바인딩을 좁힌 `resolved_indirect_call`, 같은 객체 또는 확인된 별칭의 상태 필드 쓰기·읽기를 잇는 `field_flow`를 별도 입력 버전으로 검증한다. **같은 타입의 필드를 참조했다는 사실만으로 `field_flow`라고 표시하지 않는다.** 직접 호출은 호출 위치, 간접 호출은 호출과 바인딩 위치, 필드 관계는 쓰기·읽기·객체 연결 위치를 각각 `evidence`에 넣는다. 연결을 입증하지 못한 후보는 모델 입력에서 빼고 실행 기록에 `unresolved`로 남긴다. `evidence.code`는 지정된 원본 줄의 문자 그대로이며 오류 추정이나 취약점 설명을 덧붙이지 않는다.

모델에 보내는 `questions`는 다음 **단일 Noul**을 제안한다.

```json
{
  "review_target_with_context": {
    "type": "noul",
    "instructions": "Is the target function worth a security researcher's time to inspect further for bugs based on the provided code?"
  }
}
```

1차의 “this function”을 그대로 쓰면 관련 함수가 추가된 상태에서 판단 대상이 모호하다. 2차는 `target`을 명시하되 조사 가치라는 판단은 유지한다. 따라서 1차와 2차의 **절대 점수 차이를 맥락만의 효과로 해석하지 않는다**. 같은 앵커의 순위, 알려진 기전 도달, 처리량을 비교한다. Jev는 경로 설명이나 버그 위치를 반환하지 않으므로 `Noul` 응답에서 이를 만들어 내지 않는다. [질문 형식 문서](https://docs.typesafe.ai/primitives)

## 직렬화와 한도

- 모델 입력의 필드 순서는 `target` → `related_functions` → `relations`로 고정한다. 관련 함수는 선택 규칙의 순서대로 `R1`, `R2`를 붙이고 관계·근거는 종류, 출처 위치, 대상 키 순으로 정렬한다. 객체를 공백 없이 UTF-8 JSON으로 직렬화한 **실제 `state` 바이트**를 해시와 한도 계산에 사용한다.
- 앵커와 관련 함수 본문을 자르지 않는다. 관계 근거만 완전한 함수가 아닌 원본 줄 발췌를 허용한다. 같은 함수는 한 번만 넣고 여러 관계에서 같은 키를 참조한다. 코드는 입력 스냅샷의 원본 파일·줄과 바이트 단위로 대조한다.
- 기존 A 설계의 **`state` 28,000 UTF-8바이트 목표 상한은 검토할 제안**으로 유지한다. 앵커와 빈 배열이 이 상한 안에 들면 관련 함수를 하나씩 완전하게 추가하고, 넘는 후보는 함수 전체를 빼며 이유를 기록한다. **앵커만으로 28,000바이트를 넘는 경우에는 앵커 전체만 보낸다.** 이 예외는 `anchor_only_over_budget`로 기록하고 관계 맥락이 없음을 결과에 드러낸다. 실제 API가 입력 한도를 거부하면 `oversize`로 2차 미평가를 기록한다. Expat의 1차 통과 함수 `doProlog`는 본문 40,305바이트지만 1차 요청은 11,061토큰으로 성공했다. 따라서 바이트 목표만으로 이 앵커를 미평가하는 것은 불필요하다. [2026-09-24 확인한 모델 문서](https://docs.typesafe.ai/models)는 `jev-1.13.0`의 전체 요청 64k토큰, `state`와 가장 긴 질문의 합 32k토큰을 명시한다. 바이트 목표는 그 토큰 한도를 대신하지 않으므로 실제 API 사용량과 한도 오류도 기록한다. [모델의 긴 상태 관련 주의](https://docs.typesafe.ai/model-jaggedness/jev-1.13)는 관련성이 낮은 코드가 많을수록 판단 품질이 떨어질 수 있다고 설명하므로 목표 상한을 무작정 늘리지 않는다.
- 실제 7-Zip 26.01의 `MixCoder_Code`를 `target`, 직접 호출자 `XzUnpacker_Code`를 `R1`로 넣은 **형식 예시**는 15,414바이트다. 원본 함수 4,574·9,730바이트와 호출 근거 `C/XzDec.c:1071-1074`를 포함한다. 전체 예시와 소스 리비전·입력 해시는 로컬에서 Git 제외된 `runs/input-design-mixcoder-v1/`에 있다. 이 조합은 형식 검증용이며 A의 관계 선택 결과를 미리 정하지 않는다. API 호출은 하지 않았다.

## 실행 기록에 두고 모델에는 보내지 않는 값

소스 리비전, 버전·수정 상태, 1차 점수와 순위, 원래 함수 ID와 요청 안의 키 대응, 관계 후보의 선별·제외 이유, 입력 해시·바이트 수, 추출기·질문·모델 버전, 취약점 라벨·패치 근거는 요청 밖의 실행 기록에 둔다. 관계 후보가 해석되지 않았거나 한도로 빠졌다는 사실도 기록한다. 모델에는 위의 `state`와 질문만 보낸다. 입력의 누락을 숨겨 성공 처리하지 않도록 2차 미평가·부분 맥락 건수를 결과에 별도로 제시한다.
