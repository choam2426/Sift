# 2차 입력 구성과 판단 질문 비교

> 2026-09-27 상태: 네 가지 입력 구성과 다섯 질문 방향을 교차한 **20개 조건을 모두 비교**하기로 합의했다([ADR 0009](../../docs/adr/0009-compare-four-second-pass-inputs.md)). 아래 프롬프트의 정확한 문구는 첫 7-Zip 점수 수집용으로 고정했다. 기존 국소 파일럿을 이 비교 실험의 결과로 취급하지 않는다.

> 2026-09-27 실행 순서 조정: 첫 Jev 점수 수집은 탐색 실험으로 진행한다. 이 단계에는 질문 문구와 호출 횟수만 정하면 된다. 3차 모델·조사 예산·판정 기준은 3차 비교를 시작하기 전에 정한다. 첫 점수만으로 네 방식의 취약점 검출 성능에 대한 최종 우열을 주장하지 않는다.

## 판단 질문 — 첫 7-Zip 실행용으로 고정

아래 질문들은 서로 다른 성질을 측정한다. 같은 Noul 형식이어도 점수의 의미가 같다고 보거나 임의로 평균하지 않는다. 입력은 코드와 확인된 관계이며, 실패를 암시하는 해설이나 정답 라벨을 덧붙이지 않는다. 질문별 독립 요청은 비교 방식의 제안이다. 2026-09-27 논의에서 단일 Noul 점수만으로 안전해 보이는 경우와 근거가 부족한 경우를 완전히 분리할 수 없다는 한계를 인정했다. 이는 Jev의 출력 계약에 따른 실험 해석 한계로 기록하고, 미해결 관계와 미평가는 점수 밖에서 별도로 보존한다. 이 한계를 이유로 임의의 점수 보정은 하지 않는다.

공통 지시문:

2026-09-27 독립 검토에서 설명 출력을 요구하는 듯한 동사와 반복 지시를 줄이고, P1은 안전 조건의 위반, P5는 유발 조건에서 유해한 결과까지 이어지는 구체적인 실패로 초점을 구분했다. 두 질문의 대상이 겹칠 수 있으며 상호 배타적인 결함 분류는 아니다. `matrix_questions.json`과 아래 문구는 첫 7-Zip 실행에 동일하게 적용한다. 상태는 `frozen_for_experiment`이며, 이전 `runs/*-prepared-*/` 요청 목록에는 옛 질문 해시가 남아 있어 사용하지 않는다.

### P0: 직접 취약성 질문 — 기존 비교 기준

기존 파일럿의 질문과 해시를 보존해 비교 기준으로 사용한다. 새 대안과 같은 질문이라고 합치지 않는다.

### P1: 안전 조건 위반

> Does the code support a violation of a security-relevant safety condition, such as a bound, lifetime, or consistency requirement? The condition and how an operation can violate it should be grounded in the supplied code.

예: 결과 길이가 실제 출력 범위와 일치해야 한다는 조건이 코드상 유지되는지. 장점은 취약점 명칭보다 성립해야 할 조건에 초점을 맞춘다는 점이다. 필요한 조건을 모델이 잘못 추정하거나 외부 계약을 지어낼 위험이 있다.

### P2: 함수 사이 계약 불일치

> Does a caller supply arguments or use a callee's result or side effects in a way that conflicts with the callee's behavior or requirements, with a security-relevant consequence? Ground the mismatch in the code on both sides of the call.

예: 반환값이 이번 호출의 처리량인지 누적 처리량인지에 대한 호출자와 피호출자의 해석 차이. 여러 함수를 묶는 2차의 이점을 직접 시험한다. 호출 경계 양쪽의 근거가 필요하며 한 함수 내부에만 있는 문제를 충분히 다루지 못한다.

### P3: 검사와 실제 동작의 불일치

> Can an operation cause a security-relevant failure despite a preceding check intended to constrain it? Consider whether the check covers the value, object, and action actually used, including changes between the check and use.

예: 검사한 값이 이후 변경됐는데 실제 동작은 변경된 값을 사용하는 경우. 검사 존재 여부보다 검사와 사용의 연결을 평가한다. 검사 자체가 없는 문제나 다른 종류의 결함에는 적용성이 낮다.

### P4: 상태 전이의 불일치

> Can initialization, updates, use, or cleanup put an object in a state that a subsequent operation uses incorrectly, with a security-relevant consequence? Ground the sequence and the connection between accesses to that object in the supplied code and relations.

예: 초기화·재사용 시점과 누적 상태의 의미가 맞지 않는 경우. 반복 호출과 객체 수명에 관한 맥락을 평가한다. 코드에 근거가 없는 호출 순서를 모델이 가정하지 않도록 검증해야 하며 순수 계산 후보에는 적용성이 낮다.

### P5: 구체적인 실패 기전

> Does the code support a concrete security-relevant failure in which a triggering input or state leads through an incorrect operation to a harmful consequence? Consider the connection from trigger to consequence, including checks and error handling that may prevent the failure.

예: 어떤 입력·상태에서 어느 계산이나 갱신이 잘못된 결과를 만드는지 연결할 근거가 있는가. 유발 조건·잘못된 연산·유해한 결과의 연결이 코드로 뒷받침되는 실제 실패인지를 묻는다. P1이 성립해야 할 안전 조건을 출발점으로 삼는 데 비해 P5는 전체 실패 기전을 중심으로 판단한다. 완전한 증명이나 재현 결과를 요구하지 않으며, 조사 가치나 가설 생성 가능성을 채점하지 않는다. 넓은 질문이므로 그럴듯한 추측에 점수를 줄 위험은 여전히 있다. 출력은 Noul 하나다.

P2는 호출 경계, P3는 선행 검사와 사용, P4는 동일 객체의 상태 변화라는 근거가 있는 후보에서 해석하기 쉽다. 이 구조가 없거나 입력에서 확인되지 않아 낮은 점수가 나와도 후보 전체가 안전하다는 뜻은 아니다. 적용 여부를 별도 출력으로 요구하지 않고 다섯 질문을 모든 후보에 그대로 적용하는 제안이며, 단일 Noul로 적용 대상 아님·근거 부족·위반 근거 없음을 구분할 수는 없다. 공통 지시문의 불확실성 표현도 이 출력 한계를 해결하거나 특정 중간 점수를 뜻하지 않는다.

## 아직 정할 사항

- 구현한 후보 경계와 정규화·중복 규칙의 실행 전 검토·확정.
- 후속 사례에서 질문을 다시 사용할지 여부. 첫 7-Zip 실행의 공통 지시문과 P1~P5 문자열은 위 문구로 고정했다.
- 범용 질문과 특정 기전 질문을 각각 비교할지, 조합한다면 어떤 의미와 규칙으로 조합할지.
- 사례 구성, 독립 반복 횟수, 3차 예산과 판정 기준.
- 근거 부족이 낮은 점수에 섞이는 문제를 어떻게 측정할지. 입력의 미해결 관계·미평가 정보는 점수와 별도로 보존한다.

## 실험 코드 작성 계획 — 제안

> 2026-09-27 검토용 구현 계획. 아래의 후보 경계와 실행 수치는 합의된 규칙이 아니다. 위의 4×5 비교 결정을 구현 가능한 작업으로 나눈 것이다.

1. **입력 스냅샷 검증기:** 사례별 소스 리비전, CodeQL DB·QL 팩/질의 버전, 함수 목록과 1차 `selected.jsonl`의 해시·평가 범위를 기록하고 맞지 않으면 중단한다. 최초 점검은 기존 7-Zip 26.01의 55개 C 파일과 376개 출발 함수에 한다. 다른 언어의 사례도 같은 계약으로 추가하되, 현재 C/C++ 국소 질의가 Rust·Go 관계를 이미 추출한다고 가정하지 않는다.
2. **중립 코드 사실 내보내기:** 함수·선언·직접/간접 호출 위치, 인자·반환값, 값 의존, 객체·필드 접근, 조건이 제어하는 효과, 관찰 가능한 효과를 원본 위치와 함께 정규화한다. `db_extracted`와 `ql_derived`를 구분하고 QL 모델·설정, 추출 범위와 미해결 관계를 남긴다. 원본 소스 범위와 대조한 뒤 사실 스냅샷을 고정한다. CodeQL 보안 질의·경고·패치·취약점 라벨은 이 단계에 넣지 않는다.
3. **네 후보 생성기:** 같은 사실 스냅샷과 출발 함수 목록을 받아 호출 경로, 값의 유입에서 효과까지의 의존, 동일 객체 상태의 초기화·변경·사용, 관찰 효과에서 역으로 찾은 기여 관계를 각각 후보로 만든다. 각 방식의 진입과 종료 조건, 관계가 갈라질 때의 후보 분리·합치기, 미해결 관계의 처리는 구현 전에 예시와 함께 정확히 고정한다. 함수 수·호출 홉·토큰 크기를 후보 경계로 사용하지 않는다. 완전히 같은 후보는 정규화한 동작 경계·관계 근거·코드로 합치고 모든 출발 함수와 입력 방식의 출처를 보존한다.
4. **공통 후보 패킷과 Jev 상태:** 후보에는 동작 경계, 전체 함수 본문, 필요한 선언, 함수 사이 관계의 근거, 미해결 의존성을 둔다. CodeQL의 원시 접근·조건 목록처럼 본문에 이미 보이는 자료는 사실 스냅샷에 보존하되 Jev 상태에는 반복하지 않는다. `candidate_id`와 실제 전송 `state_sha256`을 분리한다. 동일 패킷을 2차가 점수화하고 3차가 조사 시작 입력으로 사용하며, 3차는 필요한 코드를 추가 조회할 수 있다. 입력 크기와 실제 토큰 수를 기록하고 API 거부는 미평가로 남긴다.
5. **질문·실행기:** P1~P5의 정확한 영문 문자열, 공통 지시문, 모델·반복 횟수·재시도 정책을 버전과 해시로 고정한다. 후보 패킷은 질문과 무관하게 먼저 생성한다. `(입력 방식, 후보 ID, 질문 ID, 반복)`을 요청 키로 삼아 Jev에 단일 Noul 질문씩 보내고 원시 응답·사용량·오류·지연을 저장하며 중단 후 재개할 수 있게 한다. 이전 P0 질문은 별도 과거 비교 자료로 둔다.
6. **평가·감사:** 모델 입력을 고정한 뒤에만 숨긴 기전 라벨로 필수 코드 포함·누락을 감사한다. 방식별 후보 수·중복·미해결·미평가를 먼저 보고한다. 질문의 적용 범위 차이를 기록하고 조건별 Noul 평균을 성능으로 쓰지 않는다. 3차의 동일 모델·조회 도구·조사 예산을 먼저 고정한 뒤 각 조건의 상위 후보를 조사해 확인된 기전 도달, 근거 있는 미확정 후보, 비용을 비교한다.

기존 `pilot_codedb_state.py`, `augment_codedb_pilot.py`, `build_lean_codedb_pilot.py`는 특정 7-Zip 함수·임시 CSV·고정 출력 경로를 전제로 한 국소 검증 코드다. 중립 질의와 소스 위치 대조 로직을 참고하되, 네 후보 생성기의 공통 기반으로 그대로 사용하지 않는다. `score_codedb_pilot.py`의 요청·응답 검증과 해시 기반 재개 방식은 새 실행기에 옮길 수 있다. 구현 점검은 먼저 모델 호출 없이 후보 생성의 결정성·원본 위치·중복·누락을 확인하고, 이어 소수 후보에서 질문/응답 계약을 확인한 다음 고정한 실험 범위에 실행하는 순서로 한다.

네 후보 생성기의 **검토용 규칙**을 코드로 옮겼다. 7-Zip은 동일한 376개 출발 함수에서 호출 746개(출발 함수 217개), 값 1,779개(341개), 상태 224개(132개), 효과 1,828개(347개)의 후보를 만들었다. TinyXML2는 동일한 54개 출발 함수에서 차례로 196개(46개), 105개(46개), 26개(15개), 93개(45개)였다. 후보가 없는 출발 함수는 각 방식의 커버리지 공백으로 기록하며, 숫자를 맞추기 위해 경계를 바꾸지 않는다.

`prepare_matrix.py`와 `run_matrix.py`의 모델 호출 없는 검증에서 7-Zip `runs/matrix-7zip-26.01-prepared-v5/`는 **1회 반복 22,885개 고유 요청**, TinyXML2 `runs/matrix-tinyxml2-10.0.0-prepared-v2/`는 **2,100개 고유 요청**으로 확인됐다. 둘 다 완료된 Jev 호출은 0개다. 이 숫자는 점수나 검증 성과가 아니다. 7-Zip의 숨긴 CVE 라벨로 입력 포함만 감사한 결과 필수 코드를 모두 담은 후보는 호출 방식 7개, 상태 방식 1개였고 값·효과 방식은 0개였다. 이 결손을 점수로 보정하거나 해당 라벨에 맞춰 후보 규칙을 조정하지 않는다.

### 첫 7-Zip 점수 수집 — 2026-09-27 중단 상태

검토한 P1~P5 문구를 `frozen_for_experiment`로 고정하고 동일한 후보 입력에서 새 요청 목록 `runs/matrix-7zip-26.01-prepared-v6/`을 만들었다. 후보·질문 조합당 1회씩 **22,885건**을 계획했다. 20,487건의 응답 기록 중 18,882건은 Noul 점수, 220건은 `max_tokens_exceeded` 미평가, 1,385건은 HTTP 402 오류다. 나머지 2,398건은 전송하지 않았다. 첫 HTTP 402는 응답 19,103번째에서 나타났고 이후의 응답도 같은 상태여서 호출을 중단했다. 사용량이 보고된 성공 응답의 합계는 입력 110,734,835토큰, 출력 396,522토큰이다. 세부 수치와 응답 파일 해시는 무시 대상 실행 디렉터리의 `run-status.json`에 기록했다.

HTTP 402의 계정 측 원인은 이 저장소에서 확인할 수 없다. 외부 계정 상태가 해결되기 전에는 재호출하지 않는다. 실행기는 새로운 402가 발생하면 즉시 추가 요청을 멈추도록 수정했으며, 기존 402 요청을 다시 평가할 때는 `--retry-http-402`를 명시한다. 전체 조건의 점수가 아직 없으므로 질문·입력 방식의 우열이나 알려진 사례의 최종 순위를 보고하지 않는다.

사용자가 확보한 점수만으로 평가하기로 한 범위와 결과는 [7-Zip 부분 평가](partial-results-7zip-2026-09-27.md)에 남겼다. 그 문서의 순위는 채점된 후보 안에서만 계산한 탐색 결과다.

부분 평가 후 후속 질문은 P2·P3·P4를 우선 검토한다. 이는 7-Zip 한 사례의 임시 축소이며 원래 4×5 입력·질문과 점수 파일은 변경하지 않는다. 다른 사례에서의 적용 범위와 누락을 보고 최종 질문 집합을 판단한다.

현재 구현에서 함수 간 값 이동은 정적으로 확인된 인자→매개변수, 반환값→호출 결과와 가능한 국소 영향만 나타낸다. 상태 방식은 정확한 포인터 전달만 연결하므로 C++의 `this`·참조·별칭 관계가 빠질 수 있다. 함수 포인터·동적 호출의 대상과 동일 런타임 객체도 충분히 증명되지 않으면 미해결로 남긴다. Rust·Go의 동등한 의미 사실 추출과 네 후보 생성은 아직 준비되지 않았으며, TinyXML2의 2차 정답 라벨도 없다. 첫 7-Zip 점수 수집의 질문 문자열과 호출 횟수를 정한 뒤 새 요청 목록을 만들고 실행한다. 3차 모델·도구·예산·판정 기준은 실제 3차 비교 전에 정한다.

### 독립 후보 경계의 첫 구현 규칙 — 실행 전 검토 제안

2026-09-27 사용자는 네 방식이 후보를 독립적으로 생성하는 쪽을 확인했다. 아래 규칙을 첫 생성기에 구현했으며 실험 규칙으로는 아직 확정하지 않았다. 현재 추출 사실만으로 연결을 증명하지 못하면 후보를 억지로 완성하지 않고 출발 함수·관계·원인을 미해결 목록에 남긴다. 생성 결과의 후보 수가 달라도 네 방식에 같은 1차 출발점 집합을 준다.

| 방식 | 후보 하나의 앵커와 닫힘 조건 | 현재 확인할 누락 |
|---|---|---|
| 호출 흐름 | 1차 출발 함수의 원본 호출 지점 하나에서 시작해 정적으로 확인된 피호출자의 호출 경로가 끝날 때까지 포함한다. 같은 출발 함수의 다른 호출 지점은 별도 동작이다. 재귀 순환은 이미 방문한 함수에서 멈추고 순환 근거를 남긴다. | 형제 호출이 공유 상태를 초기화하는 관계, 간접 호출 대상 |
| 값의 흐름 | 출발 함수의 입력 매개변수 또는 필드 읽기 하나에서 관찰 효과까지의 가능한 값 의존을 한 후보로 묶는다. 인자→매개변수·반환값→호출 결과의 함수 간 이동에는 확인된 호출 위치를 요구한다. | 국소 값 단계와 정적 호출 연결만으로 완전한 함수 간 경로를 얻지 못함 |
| 상태 변화 | 출발 함수의 객체 또는 주소를 전달한 하위 객체 하나를 앵커로, 확인된 동일 객체 전달을 따라 초기화·수정·읽기·사용 함수들을 묶는다. 필드 선언만 같고 객체 연결이 없으면 합치지 않는다. | 별칭·포인터 재대입, 간접 호출의 객체 전달 |
| 효과 중심 | 출발 함수에서 확인된 반환값 또는 필드·포인터 쓰기 대상을 하나의 앵커로 삼아, 그 대상에 도달할 수 있는 값·조건·호출 근거를 역방향으로 모은다. 같은 대상의 여러 쓰기는 한 후보로 묶는다. | 대상·별칭이 가리키는 실제 객체, 외부 호출의 부작용 |

이 규칙은 홉 수나 함수 수로 경계를 자르지 않는다. 다만 호출 흐름의 전체 하위 호출 경로와 효과 중심의 모든 기여 관계는 지나치게 넓은 입력을 만들 수 있으므로, 첫 생성 결과에서 실제 코드가 하나의 동작을 설명하는지 사람이 블라인드 점검해야 한다. 그 점검을 거쳐 규칙을 바꾸면 입력 버전을 올리고 다른 사례에서 재검증한다. 라벨이나 Jev 점수로 후보 경계를 보정하지 않는다.
